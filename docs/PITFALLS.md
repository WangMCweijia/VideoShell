# 视频壳 · 踩坑总览与「通配性」清单

> 1.0.0 → 1.0.38 期间被真实站点打出来的坑，按**错在哪一层**归类。
> 每条都写成四段：**现象 → 当时的错误归因 → 真因 → 沉淀下来的通用机制**。
> 目的不是记录历史，而是让**下一个新站**少走一遍这些路。
>
> 维护纪律：新增一条坑时必须写清"通用机制"那一栏 —— 只描述现象、不给出机制的条目，
> 下一个人还会再踩一次。

---

## 0. 一句话结论

三十多个版本里，真正反复咬人的只有**一句话**：

> **能用"量"去判的，就不要用"形状"去判；能"当场测量"的，就不要"写死"，
> 也不要指望用户去手工校准。**

以及配套的三条方法论：**对照组**（错误的输入也应该出零结果）、**分层汇报**
（原始字节 vs 处理后字节）、**判据只有一份**（界面当场数出来的数 == 运行时判的数）。

## 1. 坑位总表（速查）

| # | 现象（用户视角） | 真因（代码视角） | 通用机制 |
|---|---|---|---|
| N1 | 明明图床可达，界面一片空白 | 图片本身是 AES 密文，不是图片 | 图片层解密拦截器 + 魔数判据 |
| N2 | 「自检单张图绿、界面网格全空」 | 无 DNS 记录时**每张图各查一次 DoH** | DNS 结果必须缓存 |
| N3 | 站点被误判成"不是视频站" | `Accept: application/json` 让整页被转义成 JSON | 请求头姿态固定 |
| N4 | 自检说 A、报告说 B（自相矛盾） | 走了带改写层的链路，**看不到服务器原样字节** | 分层汇报：原样链路 vs 应用链路 |
| N5 | 加了诊断信息后**故障更严重** | 往 HTTP 响应头塞中文 ⇒ 每请求都抛异常 | 诊断走日志，绝不进响应头 |
| P1 | 分类栏里全是页脚功能页（5 个） | 认"容器"只拿到导航里的功能页 | 认形状 > 认容器 |
| P2 | 分类只有 5 个（实际 40 个） | 只认用户点击的那一个容器 | 认形状可跨容器全收 |
| P3 | 分类栏混进「探索分类」这类导航项 | 导航项与真分类**形状完全相同** | 同形靠**数量**分开（≥2 别名 / ≥2 名字） |
| P4 | 新站分类栏是空的，只能去校准 | 分类形状只有"校准"和"写死的家族"两个来源 | **形状普查**：当场归纳 + 计数（v1.0.34） |
| P5 | 分集列表一条都拿不到 | SSR 数据藏在 `__NUXT_DATA__`，不在 DOM | 按**元素形态**挑数组，不按键名 |
| P6 | 卡片名是「查看更多」、图是 `data:` 占位 | 首页是客户端渲染，SSR 里没有剧集数据 | 换数据源（探真分类页），不是改选择器 |
| S1 | 「搜什么都一样」 | 搜索路由软 404 **回首页**，首页推荐位被当成结果 | **对照组**：错误的输入也应出零结果（v1.0.34 守卫） |
| S2 | 首轮搜索全军覆没后再也搜不到 | 严格遍失败 ⇒ 永久固化一个打歪的模板 | 失败时**强制重学**表单模板 |
| S3 | 搜索能出结果但"不对" | 人工校准存的模板是 200 空壳（0 条） | 200 状态码 ≠ 路由可用 |
| D1 | 详情页一点进就失败 | 模板只活在实例内存，跨 Activity 丢 | 学到就写盘（配方） |
| D2 | 站点改过目录名 ⇒ 详情必然 404 | 穷举模板永远举不全 | 从真实链接**反推形状**再固化 |
| V1 | 「自检全绿，播放全挂」 | 播放数据源退回了默认栈 | 数据源必须与网络栈共用 |
| V2 | VOD 从片尾开始播 | 补了 `ENDLIST` 被当成直播 | 只在 `isVod \|\| hadEndList` 时补 |
| V3 | 网页能播、App 播不了 | HLS playlist 不合规 | 播放前先过合规修复层 |
| V4 | 直链第二天必然 403 | 固化带 TTL 的 `auth_key` | 时效签名**只当次取用** |
| C1 | 「校准走完了，界面跟没校准一样」 | 五种完全不同的成因，界面看不出区别 | 把真实决策记下来 → 自检 `[2a]` |
| C2 | 同上，且**永远查不出** | 校准结果页「取消」是 `null` 监听，整轮静默丢弃 | 危险按钮必须二次确认 |
| C3 | 重新校准后旧规则还在 | `restart()` 漏清 `catTpl` / `navSel` | 状态复位要成对 |
| C4 | 校准写盘了但没生效 | `finish()` 没 `setResult` / 初始化顺序把配方覆写掉 | 结果回传要断言 |
| C5 | 校准"成功"却永远不生效 | 学到的形状**运行时判据必然否掉** | 校准必须**当场自证**（同源判据） |
| E1 | 加字段后行为诡异 / 默认值不生效 | Gson 绕过构造函数，Kotlin 默认值失效 | 加字段两端同步 + 显式 `@JvmOverloads` 式构造 |
| E2 | 功能"改了没生效" | **同一文件在同一回合发多个 Edit，后面的被静默丢掉** | 一个文件一次只发一个 Edit，改完 grep 数命中 |
| E3 | 编译报 `Unclosed comment` | Kotlin **块注释可嵌套**，KDoc 里写了 `/*` | 文档里写 `…/…` 不写通配符 |
| E4 | 断言 FAIL 但其实代码是对的 | 守卫断言 `contains` 把**注释里的历史文案**算成回归 | 守卫只看"会不会打印出去" |
| E5 | 差点发布一条"自信但错误"的判据 | 判据对客户端渲染页**两个方向都会错** | 错向多边的判据，比没判据更糟 |
| E6 | 等价重构后守卫报红 | 守卫**绑死了语法**（查 `html else FamilyRouter(site)` 字面量） | 守卫判**语义**，不绑写法 |
| S4 | **任何站**都会被"识别"成加密站 | 自证候选里混进了**官方线路**（它至今解得开） | 血缘判据只能用**本站自己**的域名 |
| C6 | 校准过的站又变回采集接口 | 大重写时**静默丢掉**「校准优先于 apiMode」这条既有规则 | 既有规则要有**行为**断言兜住 |
| C7 | 「点了对的分类，界面却说没识别到」 | **同一件事两套判据**：点击定性漏了尾斜杠家族，学习者却认它 | 「点击定性」必须 = 「学习者判据」 |
| C8 | 第 4 步填了词点确定，**流程不结束** | 学不到模板就 `return`；唯一能往下走的按钮写着「取消」 | 每条失败路径都**必须有终点** |
| D7 | 分集名每格都在复读剧名 | 站点给的集名自带剧名（`少妇白洁 第一集`），第一集还常没有序号 | 显示名**收敛成「第N集」** |
| D8 | 「第3集」被排到第 1 位 | 排序**逐条**回退：A 集取自集名、B 集取自地址，两个量级不可比 | 一列数字必须来自**同一个来源** |
| E7 | 集号判据抄了三份，各错一格 | 三处各写一遍"从标题取集号" | 判据只有一份：写一处，三处引用 |
| E8 | 同一个域名被重复添加成两条站源 | 判"在不在库里"用了 **key**（key 取决于当时的识别结果） | 「是不是同一个站」按 **host** 归一 |
| E9 | 用户选过的选项被静默换成另一个 | 持久化存了枚举**下标**，枚举插项后含义漂移 | 存**名字**，认不出就回默认 |
| S5 | 「全站源」搜出来的某一条点开是空的 | 影片 id 是**站点内**编号，聚合结果没带来源站 | 聚合结果**逐条带来源站**（从哪来、回哪去） |
| S6 | 「全站都没有这部片」其实是某站挂了 | 汇总只说"没有结果"，不说**几个站失败** | 失败要留痕并显示（N/M 个站有结果） |
| S7 | 全网搜索想抓搜索引擎结果页来解析 | 抓搜索引擎 = 把"站点适配问题"换成"搜索引擎适配问题" | **当网页打开**，我们只做"在网页上做我们擅长的事" |
| C9 | 从网页里点「手动校准」被静默弹回 | 校准页第一件事是 `Store.find(key)`，库里没有就 `finish()` | 入口动作前先把**依赖准备好**（ensureSite） |
| C10 | 逛网页时被替自己跳进了播放器 | 嗅探页只有"播放页"一种用法，浏览也被当成播放页 | 同一页面的两种用法要**显式区分**（browse 标志） |
| E10 | 结果页第一屏"不高亮、不藏分类标签"，切一下别的栏又自己好了 | 搜索态只在 `paintAll()` 里设，而**新增的流式路径**一次都不走它 | 整表状态要设在**每个铺内容的入口**上（不能指望某条路顺带设） |
| C11 | 校准学到的模板"怎么点都不对" | 广告浮层盖住正文、劫持点击 ⇒ 学到的是**广告链接的形状** | 网页运行时**先拦广告**再谈学习（媒体一律不拦） |
| C12 | 一个站「**无论怎么校准**，分类和播放都失败」 | 该站 HTML 里**根本没有形状可学**：RSC 空壳 + 地址簿在签名配置里 | 这一类只能走**接口适配器**，校准不是万能钥匙（v1.0.53） |
| V5 | 接口 / 详情 / 自检**全绿**，一按播放就 403 | 授权 Cookie 挂在 **API 子域**下发（`Domain=.xxx.net`），分片却在 **CDN 子域** | CookieJar **不许按 host 分桶**，一律交给 `Cookie.matches(url)`（v1.0.53） |
| E11 | 离线 harness 反射打真 Kotlin 产物：NPE 或 `NoSuchMethodException` | Kotlin `object` 的成员是**实例方法**（要 `INSTANCE`）；`internal` 会被**改名**（`名字$模块`） | harness 先取 `INSTANCE` 再 invoke；被断言的纯函数声明成 `public`（v1.0.53） |
| C13 | 换了默认兜底之后，旧兜底层的**一条规矩悄悄没了** | 替换 `return FamilyRouter(site)` 时，把上一行「Absent ⇒ 不再套路由」一起删了 | 换/插一层时**逐条清点被替换代码承载的规则**；守卫要跟着规则走（v1.0.53） |
| E12 | 加一层路由，**三处**断言同时假红 | 剥壳判据（"只剥一层 `FamilyRouter`"）在 Bs4 / Live2 / ZqFix 各抄一遍 | 判据只留一份（`Chains.java`）：断言管**谁在干活**，不管**包了几层**（v1.0.53） |
| E13 | 每次 bump 版本都有守卫假红 | 守卫钉死精确 `versionName "1.0.52"`（runui51 已纠正过同一个错，runui52 又犯） | 只守「没被回退 + 形状对」，精确值交给 `runsign.py --expect`（v1.0.53） |

   无 `mapping.txt` —— `minifyReleaseWithR8` 根本不在任务图里，因为（见 E29）
   `minifyEnabled` 那次编辑假成功、文件里还是 `false`。判据链：**APK 体积 /
   mapping.txt 存在 / dex 字符串抽查**，三样齐才算混淆真的发生了。
3. **dex 字符串抽查要带新旧对照**：新文案（本轮 `data-vs-ad` / `清扫`）必须在、
   旧文案（`两条通道都取不到更新清单`）必须不在 —— 和验包同一套方法（E24），
   只是对象从资源换成 dex。`versionName` 在 manifest（UTF-16 池），**不在 dex**，
   别放错清单。

## 2. 四处最值得说清的坑（通用化是怎么想出来的）

### ★ 坑 N1 / N4 —— 「自检单张通、界面空白」与「我的自检在骗我」

**现象**：列表 20/20 条都有封面绝对地址，DNS 正常，HTTP 200，字节数 68720 B
（很像一张正常图），**界面一片空白**。

**错误归因（连续两轮）**：
1. 第一轮归到"设备侧 DNS 污染"；
2. 第二轮归到"DoH 往返太多导致超时"。

**真因**：把字节摊开看——前四字节 `3E AA 70 8E`（不是 `FF D8 FF`），
熵 7.96 bits/byte、256 个字节值全部出现 ⇒ **这是密文**。站点图床存的就是
AES-128-CBC/PKCS7 密文，前端拿到 `arrayBuffer` 自己解密再显示。
密钥就明文躺在它自己的打包产物里，与接口那组 key/iv **不是同一组**。

**通用机制**：
- 判据从"状态码"升级为**"魔数"**（照抄站点前端那六条：JPEG/PNG/GIF/BMP/TIFF/WEBP）；
- 解密放在 **OkHttp 拦截器**里，挂在应用共用的那个 client 上 ⇒ 列表 / 详情 / 历史 /
  未来任何新封面位**一处修好**；
- 三道门控保证零成本、零回归：白名单外直接放行 → `206` 分片放行 → 已是 `image/*` 放行；
- **白名单按图床域名匹配，不按站点域名**（该站换过 3 次站点域名，图床域名一直没变）。

**顺带踩出来的 N4**：修完之后自检报告里出现自相矛盾的两句话——
`[3a]` 写"图床改回明文了"，同一份报告的 HTTP 记录写"已解密 65472→65471B"。
因为 `[3a]` 用的取图函数**挂在带解密拦截器的 client 上**，拿到的**永远已经是明文**，
它根本无从判断图床是否改回。⇒ 新增"绕过解密层"的原样取字节函数，
报告改成**分层并列**（① CDN 原样 ② 应用链路），再给四态判定。

> **可迁移的教训**：链路上每挂一个"改写层"，诊断能力就下降一层。
> 凡是需要判断"原始输入长什么样"的地方，都必须有一条**绕过改写层**的旁路。

### ★ 坑 P3 / P4 —— 「形状永远列举不完，数量永远分得开」

**现象**：用户在调试校准第 1 步点了一个分类，走完四步，提示"已完成"，
但用起来**跟没校准一模一样**。

**真因**：他点的是**侧栏导航项** `<a href="/explore/drama/">探索分类</a>`。
反推形状的函数把末段当成可变别名，老老实实泛化成 `/explore/{slug}/` ——
而站点真分类是 `/tag/{slug}/`，**两者形状完全一样**。
运行时判据要求"同一形状至少命中 2 条"，首页 330 个 `<a>` 里
前者只有 **1 条**、后者有 **252 条** ⇒ 判据正确地挡下了垃圾，
但**用户看不到任何原因**。

**通用机制（两层）**：
1. **校准当场自证**：校准界面在那一刻就调用**运行时同一个收集器**数一遍，
   命中 0/1 ⇒ 直接拒收并告诉用户"你点的是一个导航项，回去点真正的那串分类标签"。
   `-1`（数不出来）**绝不拒收**，避免误杀。拒收走"没学到"语义 ⇒ **保留旧配方**
   （点错一次 ≠ 本站没分类）。
2. **形状普查（v1.0.34）**：把这套"归纳形状 + 计数"从校准界面推广到**运行时自动**，
   与站点用什么 CMS、目录名叫什么完全无关 —— 新站不必校准也能拿到分类栏。

   它在真实首页上普查出 4 种形状，**两道阈值各挡下一类错**（这是最好的验证）：

   | 形状 | 命中 | 不同别名 | 不同名字 | 判定 |
   |---|---|---|---|---|
   | `/tag/{slug}/` | 248 | **88** | **88** | ✅ 真分类目录 |
   | `/rank/{slug}/` | 2 | **1** | 2 | ❌ 被「别名 ≥2」挡下 |
   | `/drama/{slug}/` | 5 | 5 | **1** | ❌ 被「名字 ≥2」挡下（全是「查看更多」） |
   | `/explore/{slug}/` | 1 | 1 | 1 | ❌ 两道都不过 |

   注意后两行：`/drama/{slug}/` 别名有 5 个（别名那一道过不了它），`/rank/{slug}/` 名字有 2 个
   （名字那一道过不了它）—— **两道阈值都是承重的**，少一道就会漏进一类垃圾。

> **可迁移的教训**："同形不同义"的判据突破口永远是**集合级统计量**（多少个不同别名、
> 多少个不同名字），不是更精细的形状正则。

### ★ 坑 S1 —— 「对照组」：能出结果不是证据

**现象**：**搜什么都一样**。

**当时的错误归因**：以为是解析不稳、候选模板打歪。

**真因**：站点的 `/?s={kw}` 是**软 404，直接把首页原样吐回来**。
实测连 `zzzq不存在的词` 都返回**与首页 sha256 完全相同**的页面（246747 B），
而首页自带的 58 条详情链接里恰好有 3 条含「庆余年」——
于是"严格遍"（要求结果标题含关键词）判定命中，把**首页推荐位**当成了搜索结果，
还把这条地址**固化进配方**。所有常规判据（状态码 / 条数 / 详情链接数）**全是绿的**。

**差点犯的第二个错**：我一度写下"自动学到的模板才是对的（出 58 条）"——
那 58 条是首页自己的推荐位。**是对照组把它扭回来的。**

**通用机制**：
- 守卫 `SoftMiss`：任何"结果页"与**首页签名**（长度 + 标题 + 唯一链接集合哈希）
  相同或近乎相同 ⇒ 判定为首页副本，丢弃；
- 自检 `[2b] 搜索路由自证（对照组）`：拿同一个模板发**两次**请求
  （一个像样的关键词 + 一个不可能存在的词），比两份响应是否同一个页面。
  两个方向都不会错：一致 ⇒ 路由忽略关键词；对照词零条目而真词有条目 ⇒ 路由正常。
  这对客户端渲染页同样成立（两次都是同一个空壳 ⇒ 也判"不可用"，而那是事实）。

> **可迁移的教训**：**"能出结果"不是证据，"错误的输入也应该出零结果"才是。**
> 任何一个"是否可用"的判据，都要问一句：**它在错误的前提下会不会也返回成功？**

### ★ 坑 E2 / E4 —— 排查纪律本身也是坑

- **E2**：改了代码但"没生效"的第一嫌疑是**改动根本没落盘**。
  实测踩过两次：同一回合对同一文件发多个编辑，**后面的被静默丢掉**，
  表现完美伪装成"断言写错了"。
  ⇒ 硬纪律：**一个文件一次只发一个编辑**，改完立刻用 grep 数命中数。
- **E4**：守卫断言 FAIL 时**先怀疑断言**。实测：为了讲清"上一版错在哪"而在
  **注释**里引用了旧的错误文案，`contains` 判据于是把注释算成回归
  —— 等于逼人删掉注释。
  ⇒ 守卫要判的是"**会不会打印出去**"，只看输出行，不看注释。
- **E5**：一条准备发布的探针被**撤销**了 —— 它的判据（数服务端渲染的结果链接）
  对客户端渲染页**两个方向都会错**（把首页噪声数成"可用"、把正常空壳数成"无效"）。
  ⇒ 判定一条判据能不能用，要看它**错的方向有几边**；两边都错的判据比没判据更糟。
  撤销时要留注释 + 守卫断言，防止复活。

## 3. 新站接入自检清单（照着做即可）

接到一个**新站点**时，按这个顺序走；每一步都对应上面某个坑。

### 3.1 先看它属于哪一类（决定后面所有动作）

- [ ] 抓首页，看有没有 `vodshow` / `player_aaaa` / `maccms` 指纹 ⇒ 采集接口站
- [ ] 抓接口，看响应体是不是 JSON 里的一个 base64 字段 ⇒ **加密接口站**
- [ ] 抓 `{origin}/config.json`，若响应是 `{"alg":"ed25519","payload":<base64>,"signature":…}` 信封 ⇒ **签名种子配置族**（地址簿在配置里，分类/列表/搜索/详情/播放全走 JSON 接口）
- [ ] 两者都不像 ⇒ HTML 站，走通用适配

### 3.2 HTML 站：先量，再判

- [ ] 分类：跑**形状普查**，看它提出的形状与计数（别名数 / 名字数是否都 ≥2）
- [ ] 详情：从列表页真实链接**反推**形状，别信穷举模板
- [ ] 分集：优先按**语义容器**找（`episode` / `playlist` / `选集`），
      容器名是全球通用的英文词，比 URL 形状稳
- [ ] 搜索：先跑**对照组自证**（真关键词 vs 不可能存在的词），再决定用哪条路由
- [ ] SSR 站：检查 `__NUXT_DATA__` / `__NEXT_DATA__` / `__INITIAL_STATE__`，
      按**元素形态**挑数组（不要按键名）
- [ ] 首页是客户端渲染的（卡片名是「查看更多」、图是 `data:` 占位）⇒ 换数据源，
      不要试图改选择器

### 3.3 图片与封面

- [ ] 整段取一张封面，**看前四字节**（不是看状态码）
- [ ] 不是图片魔数？⇒ 先查 `Content-Type`：`*octet-stream` + 图片路径 = 加密图床
- [ ] 加密图床 ⇒ 去站点自己的前端 bundle 里找 `key` / `iv` / `media_key` / `media_iv`
      字面量（**接口那组与图片那组通常不是同一组**），加一条配方
- [ ] 配方按**图床域名**匹配，不要按站点域名（站点会换域名，图床不会）

### 3.4 播放

- [ ] 网页能播、App 不能 ⇒ 对比两套请求栈发出的**字节**（不只是 URL）
- [ ] 检查 playlist 是否合规（`EXT-X-ENDLIST`、分片时长、`KEY` 的 URI）
- [ ] 直链带 `auth_key` / `expires` 之类 ⇒ **只当次取用**，绝不固化进列表

### 3.5 发布前

- [ ] 全量离线回归无回归；新坑要有对应断言（先写 FAIL 再改判据）
- [ ] 断言里**端到端**那几条要真过应用自己的网络栈（编译通过 ≠ 不炸）
- [ ] 核对签名与版本号（debug / release 同一把钥匙）

## 4. 通用化进度（v1.0.35 三笔债落地，v1.0.36 收「校准 / 分集名」）

从「单站补丁」变成「与站点无关的机制」：

1. ✅ **密钥自动发现**（`CryptDiscovery`）
   抓首页引用的**同源 JS**（`<script src>` + `<link rel=modulepreload>`），
   整段文本里盲搜 `key|iv|sign_key|media_key|media_iv` 的 `名字: 字面量` 形态；
   以 `key` 为锚、在 800 字符内与 `iv` 成型；键长不是 16/24/32 的一律丢掉（主要降噪手段）。
   **只提名不拍板** —— 能不能用交给「拿它去解服务端响应」自证。
2. ✅ **JS 渲染站 / 加密站的搜索**（`FamilyRouter` + 家族自证）
   降级链补上中间那一环：
   `URL 模板 → 站点自带 JSON 接口 → WebRender 预渲染 → 明确宣告不可用`。
   中间那环的判据是**「拿我们的密钥解得开它的响应」** —— 不认域名、不认状态码、不认外层形状。
3. ✅ **形状普查的固化**（`SiteRecipe.learnedCatTpl`）
   规则：**收出 ≥2 个分类才写盘**（写盘的一定是"用过且有效"的，不是提议），
   并且**活证据优先** —— 每次仍现场普查一遍，新形状排在固化值**前面**。
4. ⏳ **分集缩略图**：`Episode(name, url)` 没有 `pic` 字段 —— 要做需要加字段 + 改布局，
   并且会打断离线校验的 Java 位置构造，得单独排一轮。

### 4.1 新坑：**会轮换的东西不能当身份**

这一轮最贵的一条。野果（yeguodj 家族）把前端域名从 `yeguodj.com` 换到
`capable.fzchosdi.cc`、再换到 `agenda.fzchosdi.cc`，而白名单只列了 `yeguodj` 系
⇒ 不命中 ⇒ 悄悄退回 HTML 适配 ⇒ 而这一族**搜索只在接口里**（SSR 页面没有结果节点）
⇒ 用户看到「App 搜不到，但网页端能搜」。

三条教训：

- **会变的东西不能当判据**：域名、路径、压缩后的分包文件名、外层 JSON 形状、HTTP 状态码
  （站方对未知路径也回 200）都可能变。能自证的才可以：**「解得开」**。
- **站点可能在自己域名上反代了接口**：`{origin}/api.php/...` 实测与官方线路返回同一信封。
  所以 apiBase 要**从当前 origin 推导**，站点换域名自动跟上。
- **验过的姿势必须等于跑的姿势**：自证时带 `HANDSHAKE` 参数，运行时也得带，
  哪怕服务端根本不校验。否则"验过"这两个字没有意义。

### 4.2 更贵的坑：**自证候选里不能用"别人的域名"**

把"官方线路"（`www.yeguodj.com` 等）放进自证候选里，本意是"站点没反代时的退路"。
**那是把两件事混成了一件**：白名单站点的**取数**基址（已知是本族，找一个连得上的入口），
和未知域名的**血缘自证**（现场判定"这个站到底是不是本族"）。

实测（`_yg_family_probe.py`）——**官方线今天仍然解得开**：

| 候选 | 结果 |
|---|---|
| `agenda.fzchosdi.cc/api.php`（对照组） | 解得开（密文 77248 B → 明文 57932 B） |
| `www.yeguodj.com` / `yeguodj.com` / `www.ygdj2.com` / `www.ygdj3.com` | **全都解得开，同一份密文** |
| `www.baidu.com/api.php`（无关站对照组） | 解不开（返回 HTML） |

⇒ 于是一个**毫不相干**的站：自己域名的 `api.php` 一试就失败 → 接着试官方线 → 解得开 →
判成"自证命中" → 被路由到加密站适配器 ⇒ **用户输入 A 站、看到的是野果的内容**。
判据本身没有假阳性（无关站解不开），**是候选列表把假阳性引进来的**。

**修法**：自证候选**只能**从本站 origin 推导 ⇒ 判据收紧成"**本站自己**提供本族接口"，
"是我族"和"数据从哪来"才是同一句话。站点没反代 `api.php` 时退化成"判不出来 → 走网页解析"（漏收），
这是刻意接受的代价 —— 与「错收比漏收严重」同一条取舍。

### 4.3 附带的坑：**大重写会静默丢掉既有规则**

`AdapterFactory.create()` 这一轮被重写成五步流水线，**漏掉了 v1.0.15 定下的
「人工校准过（`calibAt > 0`）⇒ 优先于 apiMode」**。代码里那段注释还写着"校准优先于兜底"，
可相邻代码里根本没有这个判断 —— **注释在描述一个已经不存在的行为**。

是 `runbs4` 的行为断言（"校准过的同一站点 ⇒ 走网页解析"）当场抓住的，不然就发出去了。

两条纪律：

- **重写 = 重新证明**：既有规则的断言必须能**区分**"改结构"和"删行为"。
  所以断言要落在**行为**上（`worksAs(create(site), HtmlAdapter.class)`），
  而不是源码字面量 —— 源码守卫只能证明"这行还在"，证明不了"它还被执行"。
- **注释不能当证据**：注释说"优先于一切"，代码里没有这个分支 ⇒ 读代码时要按**代码**判断，
  发现不一致就当场补断言（而不是相信注释）。

### 4.4 新坑：**同一件事两套判据**（「点了对的分类，界面却说没识别到」）

用户原话：**「校准时，每一步点了对应的位置后，校准流程中有可能提示没识别到」**。

`SiteCalib.isCategoryShape(href)` 是**点击定性**用的判据（决定界面说"已选中"还是
"⚠ 这不像标准分类链接"）；`HtmlTemplates.catTplFrom(url)` 是**学习者**用的判据
（决定能学到什么形状）。两者必须说的是同一件事，而尾斜杠家族（`/tag/{slug}/`）
从 v1.0.32 起就是正式的分类形状家族 —— `catTplFrom` 分流认它、
`HtmlAdapter.collectSlashDirCategories` 按它收，**只有 `isCategoryShape` 没跟上**。

于是野果的真分类 `/tag/熟女/`：点击当下报「⚠ 这不像标准分类链接，形状没学到」，
按「确定」之后**又学得好好的**，报出形状 `/tag/{slug}/`。用户看到的是自相矛盾的两句话，
自然会来报"没识别到"。

同一类的第二处：`classify(Step.PLAY)` 用 `isPlayLink`（宽），而学习者
`playTplFrom` 只认 maccms 的 `/{目录}/{id}-{sid}-{nid}.html`。自研站的
`/drama/video/3381/ep-4/` 属于"说 GOOD、又学不到"—— 而运行时
`learnPlayTpl` 明明还有第二条路（`tplFromNumericSegment`）。

**修法**：让「点击定性」的判据与「学习者」的判据**同源**（学习路径全部复用运行时那两条函数），
并且把三种结论**分开说**：

| 结论 | 什么时候 | 文案 |
|---|---|---|
| 学到了 | 学习者真的产出了模板 | 「形状 /tag/{slug}/」 |
| **不需要学** | 站点自带判据本来就能认（maccms 的数字分类 id） | 「形状：站点自带判据已认得」 |
| 没学到（但兜底在） | 形状归纳不出来 | 「形状未识别」+ **具名**写出兜底是什么（容器 / 探嗅 / 详情页分集） |

第三行是关键：**「没学到」必须跟着"那靠什么"**。只说"未识别"就是把问题丢回给用户。

### 4.5 新坑：**每条失败路径都必须有终点**（第 4 步填了词点确定，流程不结束）

搜索校准（第 4 步）的地址是从「当前页 URL」里反推模板的。而对 SPA 站点，
站内搜索**不换页**（AJAX / `history.pushState`）——
`pushState` **不触发** `onPageFinished`，于是 `pageUrl` 一直停在很久以前那个首页上，
模板永远学不到；学不到时代码只是改一行状态文本就 `return`，**停在原地**。
唯一能往下走的按钮写着「取消」—— 没人会把「取消」理解成"跳过搜索校准、把前三步固化掉并完成"。

三处修法，缺一不可：

1. **地址取实时的**：`binding.webView.url`（`pushState` 后也会更新）+ JS 每次点击上报的
   `location.href` 都收下来，别只信 `pageUrl`；
2. **按钮文案 = 它实际做的事**：负按钮改成「跳过（直接完成）」；
3. **失败路径给一个必达终点的选择框**：`跳过并完成` / `我再去搜一次` ——
   两条路都能离开这一步。

通用纪律：**写流程时，把每一条 `return` 都问一遍"用户接下来怎么走出去"**。
只改状态文本的 `return`，在多步流程里等于卡死。

### 4.6 新坑：**一列数字必须来自同一个来源**（「第3集」被排到第 1 位）

野果的分集名是「**{剧名} 第N集**」，而且是**中文数字**（`少妇白洁 第二十一集`）。
集号判据只认阿拉伯数字 ⇒ 整列取不到号 ⇒ `EpisodeOrder` 的**逐条**回退生效：
A 集的号来自集名（`…第3集` → 3）、B 集的号来自伪地址（`yeguo://play/2275/186514` → 186514）。
两个量级根本不可比，`我能看到欲望值` 的第 3 集**被排到了第 1 位**。

逐条回退（"这条取不到就换下一个来源"）放在**排序 / 编号**里一定是错的 ——
只要同一列里混进两个来源，就有两把不同的尺子。正确写法是**整列同源**：

1. 整列都能从集名取到号且互不相同 ⇒ 用集名；
2. 否则整列试站点序号（`index` / `sort`）；
3. 否则整列用数组位置。

附带一条：`noOf()` 那个"名字取不到就退到地址"的兜底让「有任何一个取不出集号就不猜」
这道闸门**从来没关上过**（伪地址里天然有数字）—— 所以闸门必须判在**同一个来源**上。

### 4.7 新坑：**判据抄三份 = 三类站点各错一格**

"从标题里读集号"这件事，代码里原本有**三份**：
`EpisodeOrder.NAME_PATTERNS[0]`、`SsrPayload.TITLE_NO`、`YeguoMap` 里新写的一份。
三份都只认阿拉伯数字，于是：

- 野果（API 路径）整列取不到号 ⇒ 显示成剧名 + 排序错位；
- SSR 路径遇到中文数字集名时 `useTitle` 静默为 `false`，退到 `sort` ——
  而 **SSR payload 的 `sort` 恒为 1**（本文件当年就实测记下过），名字会全变成「第1集」。

已合并成 `EpisodeOrder.noInTitle`（阿拉伯 + 中文数字 + `第N{集话期回部}` 形状），三处引用。
**形状也必须保留**：`《庆余年》 第三季第一集` 里有「三」有「一」，只有形状能定出 1；
`AI短剧 窥破爱人谎言2` 末尾那个 `2` 是剧名的一部分，**不许**当集号。

合并它的理由不是"更整齐"，而是**三份副本的差异 = 三条不同的错误路径**。
遇到"这段逻辑好像在哪见过"时，先去找到那一份。

### 4.8 一条自查：**「拒收」要说清为什么不写**

`pickCategory` 在形状被拒收时**连容器一起不收**（v1.0.34 的实测：从同一次导航项点击
推出来的容器只是 `div.app-layout` 页面外壳，收下它会让 `manualNavSel` 把好用的默认判据顶掉）。
这本身是对的取舍 —— 但界面原来只说"改点真正的那一串分类标签"，
用户不知道**本次什么都没写**，也不知旧规则还在不在。

本轮改成明说：「本次**不写入任何分类规则**（写了反而会把上一次学对的规则挡掉）」。
**"什么都没发生"是最容易被误解成"坏了"的结果**，必须自己解释。

### 4.9 新坑：**判断"是不是同一个站"要用 host，不能用我们自己生成的 key**（v1.0.37）

「在网页里一键识别并添加」与「手动校准」是同一件事的两个入口，它们都先要回答
一个问题：**这个站在不在库里？**

原来的写法是问 `Store.find(key)`。而 `key` 是**我们自己的产物**，它取决于"当时识别成了什么"：

| 识别结果 | key |
|---|---|
| 有采集接口 | `base + 接口路径 + 参数` |
| 网页适配 | `base` |
| 自证成加密接口族 | 又可能换一种 |

于是同一个域名，用 key 问就会得到**"不在库里"** ⇒ 再添加一遍 ⇒ 站点列表里出现
两条指向同一个站的记录。用户的原话会是「我明明加过了，怎么又出来一个」。

**通用机制**：凡是"这是不是同一个东西"，判据必须建立在**对方的、稳定的**属性上
（这里是 host），而不是我们自己派生的标识（key 会随我们的识别路径变化）。
和 §4.1「会轮换的东西不能当身份」是同一条纪律的另一面 ——
**能被我们自己的流程改动的东西，也不能当身份**。

配套：`Store.hostOf` 是唯一的 host 提取器（`RecipeStore.hostOf` 的转发 + 裸 host 兜底），
`WebSiteKit.hostOfBase` 再做 `www.` 归一 —— 因为用户从搜索结果点进来是
`https://www.x.com/...`，而当初识别时存的是 `http://x.com`。

### 4.10 新坑：**持久化存名字，不存下标**（v1.0.37）

搜索范围（本站/全站/全网）要记住用户上次选的哪个。存 `ordinal` 看着最省事，
但它有一个**只在将来才发作**的缺陷：枚举里插一项（比如以后加「搜指定站」），
老用户的 `1` 就从"全站"变成了另一个东西 —— 用户什么都没点，选项自己变了。

**通用机制**：凡是"用户选过的枚举"，一律存 `name()`，读的时候用
"认得出就用、认不出回默认"的方式解析（`SearchScope.of`），**绝不做下标换算**。
断言里专门钉了 `of("1") → SITE`，就是防止有人"顺手"把下标解析加回来。

### 4.11 新坑：**同一个页面的两种用法，必须显式区分**（v1.0.37）

「网页嗅探模式」原来的唯一用法是**播放这一页**：认得出的正片就自动跳播放器。
现在它还要当**浏览器**用（搜全网 → 点开结果 → 逛到影片站）。
两者共用同一个 Activity、同一个 WebView、同一套候选收集，**唯一不能共用的就是"自动播"**：

- 播放用法：用户点进来就是为了播，自动播是省事；
- 浏览用法：用户点进来的每一下都是他自己的意图，替他跳走等于把他打断在自己不知道的地方。

所以加了一个 `browse` 标志，`maybeProbeAndAutoPlay()` 开头一句 `if (browse) return`。
配套三处也必须跟着分叉，否则会留下"看起来像坏了"的地方：
状态文案（不报"超时/登录墙"，因为用户不是在等嗅探）、
`MAX_TICKS` 轮询上限（浏览没有"超时"这回事）、
以及顶部返回键的语义（浏览时是"网页后退"，退无可退才关闭）。

**通用机制**：给一个已有界面加第二种用法时，先列出"它现在为第一种用法**默认**做了哪些事"，
逐条决定第二种用法要不要 —— 少改一条，用户就会在第二种用法里撞上第一种用法的贴心。

### 4.12 一条刻意的取舍：**不抓搜索引擎的结果页**

「搜全网」最直觉的实现是：把 Bing 的结果页 GET 回来，解析出链接，做成我们自己的卡片列表。
**我们不做这件事**，直接把结果页当网页打开。理由是成本结构：

| | 抓取解析 | 当网页打开 |
|---|---|---|
| 依赖 | 搜索引擎的 HTML 结构 | 只要浏览器能打开 |
| 对方改版 | **我们必挂**，且要等发版 | 零影响 |
| 反爬 / 跳转 / 同意页 | 每一个都是我们要处理的 | 交给浏览器 |
| 用户能做的下一步 | 只能点我们解析出来的 | 能点、能翻页、能再搜，还能「识别并添加」 |

这跟 §0 的结论一致：**我们擅长的是"在任意网页上做识别与嗅探"，不是"复刻别人的页面结构"。**
把不擅长的部分换成"把网页交给用户 + 把我们擅长的按钮摆在他手边"，这条线才不用年年修。

断言里为此钉了两条：`SearchScope` 里**不出现** `Jsoup` / `Http`（守卫不抓取），
以及 `isWebHost` 的**双边**判据（`notbing.com`、`bing.com.evil.cn` 都必须为 false）。

### 4.13 新坑：**断言辅助函数把「期望」和「实测」印反了 ⇒ 我会去改没坏的那一侧**（v1.0.38）

写 Java 离线断言时 `eq` 长这样：

```java
static void eq(String name, Object got, Object want) {           // ← 参数名是 (got, want)
    ok(name, Objects.equals(got, want), "got=" + got + " want=" + want);
}
```

而所有调用点都按直觉写成 `eq("标题", 期望值, 实测值)`。两件事叠在一起：

1. `Objects.equals` 是**对称**的 ⇒ 判定结果完全不受影响，162/164 条照样 PASS。
   **参数顺序错了不会红**，所以这个错误可以潜伏很久。
2. 但报错文案是 `got=` + 第 2 个实参、`want=` + 第 3 个实参 ⇒ **印出来正好颠倒**。

于是那 1 条真红的输出是：

```
[FAIL] 全都在时，最后一个站插在末尾    → got=6 want=4
```

我读成「代码返回 6，我期望 4 写错了」，就把字面量从 `4` 改成了 `6`。
**改完仍然红，因为真相是反的**：`insertAt` 返回的是 `4`（=前面两块 3+1 之和，不含自己），
`4` 从一开始就是对的，是我的"修复"把它弄坏了。

**教训一句话：报错的措辞和报错的数值一样要当判据看。**
`got=` / `want=` 一旦颠倒，"哪一侧错了"这个最基本的判断就是反的 ——
而它恰好指给你一个**编译器不会拦、测试也可能不红**的方向。

落地动作（两条都要做）：

- `eq` 参数名与打印顺序对齐成 `(name, want, got)`，文案改成 `want=… got=…`，
  并在函数上方写明「调用点统一写 `eq(标题, 期望, 实测)`」——**注释解释的是"为什么不能改回去"**。
- 判据本身钉注释：那个断言的值是 `3+1=4`（**只数排在它前面的已到达块**），
  顺带把标题写全（「= 前面两块之和 3+1，不含自己」），防止下次又有人"顺手修正"成 6。

这与 §2 的 E2/E4 是同一族坑，但更阴：E2/E4 是**守卫写错**（red 时先怀疑守卫），
这条是**守卫的"读数"错**（红的时候连"谁红"都读反了）。凡是"打印给人看"的辅助函数
（`eq`/`ok`/`banner`/自检汇报），都要有**断言级的自证**，或者至少让文案与调用点顺序一致。

### 4.14 新坑：**量错对象 = 结论无效**（"看起来的第一条分片"不是播放器会取的那条）（v1.0.39）

用户报「枫叶影院很多播放源能读到时長、一直转圈」。第一轮探针很"干净"：

```
段[0] status=200 ctype=video/mp2t magic=474011…
段[1] status=200 …  段[2] status=200 …
```

于是得出"分片都正常，不是分片的问题"。**这个结论是错的**，因为 `segs[0..5]` 取的是
**广告段**：清单开头就是 8 条 `/ad/XNjU1…/…-00001.ts`，而 `HlsPlaylistFixer`
把它们**整块剔掉**了 —— ExoPlayer 实际从那之后的第一条**正片**段开始取。

**教训一句话：量之前先算清"被测对象到底是哪一条"。**
判据（`/ad/` 正则 + 跟着剔 `DISCONTINUITY`）本来就在我们自己代码里，
复刻一遍只要十行，却能避免整个诊断走错方向。落地：`runzqseg.py` 现在按
**HlsPlaylistFixer 的同一套判据**算出保留序列，体检的是 `kept[0]`。

顺带钉住一条**反向**断言：剔广告后必须仍剩 ≥30 条正片段 ——
否则说明广告正则吃掉了正片，那才是**我们自己造出来的"播不了"**。

### 4.15 新坑：**瞬时失败和终态失败必须分开判** —— 但 402 到底算哪边，先测清楚（v1.0.39 判错，v1.0.40 纠正）

> ⚠️ **本条 v1.0.39 的结论是错的，v1.0.40 已证伪，保留在这里当作"判错一次"的记录。**
>
> 当时的结论：`cibn-edge-5g.1ljx.com` 对分片回 `402 Payment Required` 而清单 200，
> "停 90 秒再取全好了" ⇒ 判定为**限流**、会自己好 ⇒ 把 `402` 放进**瞬时表**去退避重试。
>
> 实际（v1.0.40 实测，12/12 次确定性 + 实时套件复现）：
> - 402 的正文是 `Payment required\n\nDEPLOYMENT_DISABLED`，响应头带
>   `X-Vercel-Error: DEPLOYMENT_DISABLED` ⇒ **上游部署被停用**，这是**终态**，重试永远无效；
> - "停 90 秒再取全好了"是**误读**：那一次探针换了一条线路（别名不同、不走 302），
>   不是同一件事"自己好了"。**换了个对象的两次结果不能拿来证明"自愈"。**
> - 409/402 那批"瞬时"里，用户真机连续 12 次全 402（若是随机命中，概率 2^-12）。
>
> 真正的根因是**相对分片解析基准错了**（见 4.21），与"限流"毫无关系。
>
> 所以 `PlayRetry` 里 `402` 该不该重试，取决于**它为什么会来**：
> 有些 CDN 确实用 402 表示限流（可重试），但"上游部署被停用"这一类是终态。
> 只按状态码判是不够的 —— **状态码是症状，不是诊断**。代价有界（最坏 2.1 秒）时
> 把它当瞬时留着可以接受；但**别指望它替你解决问题**（这次它只是把 402 重复了 3 遍）。

落地仍然是 `PlayRetry`（纯对象，可离线断言）+ 在 `OkHttpDataSource.open()` 里就地退避重试。
两条硬约束继续有效：

1. **`403/404/410` 必须不在瞬时表里** —— 重试只会白等，还会把"该换源"的情况拖成没有信息的转圈。
2. **最坏代价必须有界**（这里 0.6s + 1.5s = 2.1s，断言钉死 `< 3s`）。
   用"等 90 秒再试"去修"一直转圈"是把瞬时故障变成用户眼里的"这软件坏了"。

### 4.16 新坑：**重试"同一个地址"≠"重新解析"**（令牌是按会话发的）（v1.0.39）

枫叶影院 ps:1 线路的播放地址是**播放时现取**的：外壳页 `POST mplayer.php` 返回
`…m3u8?auth_key=<时间戳>-…`，清单里的分片又带 `psid=<每次不同>`。
**每次解析拿到的令牌都不一样**。

所以卡住时把同一个 URL 再取一遍是**白费**（令牌没变），必须**重新解析本集**
（再走一次 `playEpisode` → `resolve()`）换一份新令牌 —— 这也正是用户自己会做的事
（退回详情页再点一次）。

两个反直觉的细节：

- **自愈的次数上限不能被自愈自己清零。** 自愈走的也是 `playEpisode` → `playUrl`，
  而 `playUrl` 会把 `stalledSwitched` 之类的标志复位 ⇒ 拿它当上限等于没有上限，
  一次卡住会**无限重解析**下去。所以另开一个只增不减的 `stallReResolveTries`，
  **只在用户发起的换集/换源时清零**（`playEpisode(index, autoHeal = false)`）。
  "用户动一下 = 给一次新的自愈预算"。
- **嗅探源不走这条路**：它有自己的候选队列与换源逻辑，两套自愈会互相打架。

### 4.17 一条纪律：**"转圈"这两个字里没有任何可查的东西**（v1.0.39）

卡住面板原先只说"已缓冲 X / 共 Y / 地址 = …"。这对用户和对我都等于没说 ——
分片是被拒（402/403）、超时了，还是压根没人回？三者要做的事完全不同。

落地：面板带出 `NetLog.lastFailure()`（`HTTP 402 … @ <url>`）。
**不是锦上添花**：这次问题拖了几轮，唯一原因就是每一轮拿到的都是"转圈"两个字。
凡是"用户描述里没有任何可查信息"的现象，第一件事是**把它变成一条可读的读数**。

### 4.18 一条 UI 细节：**网格里的分组标题必须独占整行**（v1.0.39）

聚合搜索按站分块，块之间要加一行"站名 + N 条"。但容器是
`GridLayoutManager`（竖屏 3 列 / 横屏 5 列）—— 不给 `SpanSizeLookup` 的话，
标题只占一格，和卡片并排，**分组边界比不加标题还糊**。

配套：适配器要暴露 `isHeader(position)`，`getSpanSize` 只认这一处判据
（别在 Activity 里再判一次 `rows[pos] is Header` —— 那是第二套判据）。

### 4.19 一条断言纪律：**不要写 vacuous 断言**（v1.0.39）

给 #1（搜索不显示分类标签）写断言时，因为渲染要真机，顺手写了两条：

```java
ok("VideoAdapter 暴露 setSearchKeyword（唯一入口）", true);
ok("hideTags 与 highlight 由同一个方法一起设 ……", true);
```

它们**永远绿、且什么都不验** —— 比没有断言更糟：报告上多两行 PASS，
读的人会以为这条已经验过了。

落地：撤掉，改成一条明确的 `[SKIP]` 说明"渲染需设备"，并把**能离线验的部分**
（一个入口、各**一个**写入点、副标题里真的按 flag 分流）全部搬进源码守卫，
那里数的是**活代码**。**能验的必须验，不能验的必须说清不能验 —— 不许用 PASS 糊过去。**

### 4.20 单位变了，不变量要在新单位里**重证**（v1.0.39）

`AggSearch.insertAt` 从"卡片数"改成"**行数**"（每块多一行标题）：
`h0(3 卡)` 的插入点从 `3` 变成 `4`。旧断言（Agg38 D 段）里那几个字面量
必须一起改，**但改数字不等于放弃断言** —— 同时在**行空间**重立同一条不变量
（任意到达顺序铺出来的网格 == 一次性 `mergeRows`），并补一条
**投影断言**：`mergeRows(...)` 的卡片投影必须逐条等于 `merge(...)`。

这样"两份判据同源"这句话才是可执行的，而不是一句注释。
**改契约时，断言要跟着换空间，不能只跟着换数字。**

### 4.21 ★ 最贵的一条：**相对地址必须按「重定向后的最终地址」解析**（v1.0.40）

**症状**（用户真机，枫叶影院第 3 线路 =「蓝光2k」，`from=co`）：
清单 GET **200**、时长读得到，但**每一个分片都 402**，每片退避重试 2 次仍 402，
画面一直转圈；而**同一条线路在网页端能播**。

**根因**（12/12 次确定性，与请求头完全无关 —— 9 种头/UA/Referer 组合里 7 种 402）：

```
请求清单  https://…/cloud/flv/<a>/<b>/x.m3u8?auth_key=…
   └─ 302 → https://…/ufile/flv/qq/<长hash>/<name>_@lirose_tv.m3u8        ⇒ 200（openresty）
清单里的分片是**相对地址**：`<sid>-N.ts?tg=@lirose_tv`
   ├─ 以【请求地址】为基准 ⇒ …/cloud/flv/<a>/<b>/<sid>-N.ts
   │      └─ 又 302 → https://www.aibox.eu.org/110（无关第三方域名，Vercel 部署已停用）
   │             ⇒ 402 Payment required / DEPLOYMENT_DISABLED   ← App 的现状
   └─ 以【最终地址】为基准 ⇒ …/ufile/flv/qq/<hash>/<sid>-N.ts
          ⇒ 200，1 690 120 B，Content-Type: video/MP2T，首字节 0x47   ← 真分片
```

网页播放器（hls.js）用后者 ⇒ **"网页能播、App 转圈"的分界就在这里**。

**为什么值得单列一条**：这个 bug 的每一层都长得像别的东西 —— 像限流（402）、
像防盗链（换头无效）、像分片坏了（清单一切正常）、像解析失败（地址明明拿到了）。
它不是网络问题、不是请求头问题、也不是站方资源问题，**是我们把相对分片拼到了错的目录上**。

**落地**：判据只有一句 —— **服务器最后把清单放在哪，分片就相对于哪里**。
`OkHttpDataSource` 早就把「跟随重定向后的地址」记在 `currentUri`（`getUri()` 返回它，
这是 Media3 `HttpDataSource` 的契约），我们只是在 `HlsFixDataSource` 里**没用它**，
而是拿了 `dataSpec.uri`（我们发出去的那个）。

```kotlin
// HlsFixDataSource.open()
val len = upstream.open(dataSpec)
val servedUrl = runCatching { upstream.uri?.toString() }.getOrNull()   // ⚠️ 必须紧接 open 取
val base = HlsPlaylistFixer.baseFor(dataSpec.uri.toString(), servedUrl)
```

三个必须一起做的动作：

1. **判据抽成纯函数** `baseFor(requestUrl, finalUrl)`（`finalUrl` 空/空白 ⇒ 退回请求地址）
   —— 这样才能被离线断言逐条钉住，也能被源码守卫盯住"有没有真的被调用"。
2. **换了基准要留痕**（`PlayLog` 一行"清单被重定向 ⇒ 分片基准改为 …"）。
   这类故障的症状（分片 402/404）与"流坏了"**一模一样**，只有这行字能一眼定性。
3. **反向断言**：用两种基准跑同一份清单，产出**必须不同**。
   否则哪天有人把 `baseFor` 改成恒等，全部断言照样绿。

**顺带纠正一条方法论**：本次能查到，靠的是**始终追问"我测的这个对象，是不是播放器真正会取的那个"**
（见 4.14）。第一次测分片时我拼的是**请求地址**下的分片，测出来的 402 被我当成了"CDN 限流"；
把基准换成最终地址，同一个分片立刻 200。**同一个 URL 名、不同的拼接基准 = 两个不同的对象。**

（已知残留：**master playlist 仍原样透传**，它的变体地址由 ExoPlayer 自己解析，
若 master 也被 302 到别的目录，同样的错会以"变体取不到"的形式出现。本次未动 ——
既有断言 `HdFix` 明确要求"master 字节级未被改动"，改动它需要单独论证。）

### 4.22 一条纪律：**"它自己好了"必须证明是同一个对象**（v1.0.40）

v1.0.39 有一条结论是"停 90 秒再取，402 全好了 ⇒ 判定为瞬时限流"。
实际上那两次探针**换了一条线路**（不重定向的那条）—— 对象变了，结论自然失效。

**"同一个东西，前后两次结果不同"才是自愈的证据。**
换域名、换线路、换别名、换拼接基准之后得到的差异，属于**两个对象之间的差异**，
只能说明"这两个不一样"，不能说明"它自己会好"。

配套做法：探针里把**被比较对象的指纹**打出来（完整 URL、host、基准目录），
不要只看"这次成功了吗"。

### 4.23 一条纪律：**上游的 302 会把"一个地址"变成"两个地址"**（v1.0.40）

排查时要主动问一句：**这个地址被重定向了吗？跳到哪？**
`curl` 默认不跟随（看到 302 本体），Python `requests` 默认跟随（看到跳转目标的 200/402）——
**同一行代码、两种工具，会给出两个"事实"**，而我们之前用的两次探针恰好各占一边，
于是"清单 200 但分片 402"这种自相矛盾的现象被当成了"CDN 抽风"。

固定动作：**先看跳转链**（`r.history` / `curl -w '%{http_code} %{redirect_url}'` / `-L` 对照），
把"请求地址"和"最终地址"分开记录，再谈别的。

### 4.24 ★ 断言钉「实现位置」⇒ 重构一次就假红，而功能一直是好的（v1.0.50）

v1.0.41 立的三条断言钉的是 `reload()` **里那一刻的写法**（`val searching = mode == MODE_SEARCH`
加两行可见性赋值）。v1.0.50 把这三行抽成 `applyCatVisibility()`（一次重构，行为逐字节不变），
三条断言**全红**。全量回归从 `FAIL=0` 变成 `FAIL=3`，看起来像"这版改坏了"。

危险的不是假红本身，而是**处理方式**：最省事的做法是把代码改回去、把判据重新撒开 ——
那正好把 v1.0.50 刚收口的"唯一出口"又拆了，用一次假红换回一个真 bug。

固定动作：**断言钉「行为 + 唯一性」，不钉「某个函数里恰好长什么样」。**
真需要位置判据时（比如"先写缓存再判代次"，先后顺序**本身**就是那个行为），
在断言旁边写明"为什么这里的顺序就是行为"，否则下一个人会把它们当成可随意挪动的实现细节。

### 4.25 没有报错的那类问题：**重复请求**只能靠「路径」守（v1.0.51）

用户报的是「每点一个站源都需要重新搜索」。这件事在**任何一层都是绿的**：
不抛异常、结果一字不差、自检全过、手工点也"有东西出来" —— 错的只有**次数**。
所以它不能被"结果断言"守住，只能守**路径**：

- **换栏这条路上不许出现发起请求的东西**（`search(` / `adapterFor(` / `AggSearch.run`
  在 `selectRail()` 的函数体里一个都不许有）—— 这是**结构性**断言，比"结果一样"强；
- **顺手产物要留痕**：聚合那一趟已经把每个站的第 1 页发出去过了，那份数据必须被存下来
  给单站栏复用，而不是让它随着协程一起丢掉；
- **迟到 ≠ 作废**：用户切走了的那次请求**仍然写缓存**（只失去改界面的资格）。
  这里有个反直觉的次序 —— **先落盘、再判代次**，判在前就等于把这次请求白扔了。

配套的一条：**布尔量的 `loading` 拦不住"哪一轮是旧的"**。v1.0.50 的 `if (loading) return`
会把用户点的那一栏**静默丢弃**，而左栏高亮已经移过去了 —— 界面在撒谎（比慢更糟）。
换栏必须能被"作废 + 照跑"地接住，所以用**代次计数**：旧的失去改界面的资格，新的照常发。

### 4.26 「取函数体」这件事有边界：表达式体 / 无花括号声明（v1.0.51）

断言套件里按花括号配平取正文的 `body_of()`，遇到**表达式体**（`fun f(...): T = expr`）
与**无花括号的类声明**（`private class C(` 构造参数表）会去找**别处**的 `{`，
取回一段毫不相干的代码 —— 症状是断言**莫名其妙地红**，而代码完全正确。
（本版一次踩了三条：`AggSearch.complete` 两条、`SearchActivity.railKey` 一条。）

固定动作：拿不准就先打印取回来的正文长度/首行；这两类声明改用"签名 → 下一个空行"切。
另外 **`find()` 找的是第一处**：函数体里有两处同形状的 `if (seq == loadSeq)` 时，
位置判据要指明是**哪一处**（收尾那处），否则判据会整个反过来。

### 4.27 ★ 新路径铺结果时，**必须自己把状态设上**（不能指望另一条路顺带设）（v1.0.52）

给聚合结果加"流式铺"（先出结果的先显示）时踩到的：搜索态的**唯一设置点**在
`paintAll()` 里（`setSearchKeyword(keyword)` = 关键词高亮 + 隐藏分类标签），
而 `paintAll()` 只在**缓存命中**那条路（`render`）里跑。流式这条路是
`commitArrived()` → `insertBlock()` 逐块插，**一次 `paintAll` 都不走** ⇒
进入结果页的第一屏：不高亮、**分类标签不藏**（v1.0.39 的行为静默丢了）。
切一下别的栏再回来就"自己好了"（那次走的是 `render`）—— 最容易让人归因成"偶发"。

这类坑的判别式：**"这个行为是谁设的"**。如果答案是"某条特定路径顺便设的"，
那么任何**新增的路径**都会默认丢掉它，而且编译绿、自检绿、结果看起来也有。

固定动作：把这类"整表状态"设在**每一个真正铺内容的入口**上。本例把
`setSearchKeyword` 移到 `commitArrived()` 的 `insertBlock` 之前 —— 它是纯字段赋值
（无 notify），重复设无代价，所以铺块入口都设一遍是安全的。
判据写成**位置断言**（设搜索态必须排在插块之前，且就在插块那个函数里），
这样将来再加第三条铺内容的路径，漏设会当场红。

### 4.28 网页运行时去广告：**先给"拦错"定价，再决定拦什么**（v1.0.52）

嗅探页和校准页是全 App 唯一**真的把第三方站点跑起来**的地方（WebView），而它们要用户
做的事偏偏是"在网页里点一下正确的东西"。广告浮层会把这三点全弄坏：透明层劫持点击
（校准学到**广告链接的形状**）、广告播放器先于正片发 m3u8（污染候选清单）、
"3 秒后跳转"的弹窗把用户从正文里带走。

三条**自我约束**比"拦得多"重要得多，因为两侧代价完全不对称：

1. **媒体一律不拦**，而且这条判据**排在广告判据之前**。漏拦一个广告 = 少省一次请求；
   误拦一个分片 = 播放挂掉。代价差一个量级，所以顺序本身就是设计。
2. **不广谱隐藏 DOM**：只针对"我们自己判定为广告的那些主机"的 iframe + `adsbygoogle`
   这一种公认容器。`[class*=ad]` 那类写法会把 `/thumb/`、`ads-container` 这些**正文**容器
   一起藏掉 ⇒ 用户点不到任何东西，症状是"校准卡在第一步且没有任何提示"（静默失效）。
3. **判据与产出同源**：`hideCss()` 的选择器由 `AD_HOSTS` 生成，不另抄一份域名列表。

结构上把判据与运行时**拆成两个文件**：`AdBlock`（纯逻辑，**不 import 任何 Android 类**）
+ `WebAdBlock`（WebView / SharedPreferences 外壳）。这样整套规则能在离线 JVM harness 里
对**真编译产物**逐条断言（`runadb.py`），而不只是"源码里看着像"。

拦下来的东西**必须留痕**（进 `NetLog` + 报告里一行统计）：这类"看不见的过滤"如果只体现
在结果上，事后根本分不清是站点的问题还是我们的问题（本项目吃过太多次）。

另外两条顺手记下的：
- **空响应 ≠ 不发请求**：`shouldInterceptRequest` 里被拦的资源要返回一个**空响应体**，
  否则 WebView 认为请求还没结束，页面会半死不活（脚本停在"加载中"）。
- **表达式体的函数**在 `shouldInterceptRequest` 里很常见（`= if (...) ... else null`），
  它没有花括号 ⇒ 见 4.26，断言别用 `body_of()` 去取（v1.0.52 又踩一次）。



### 4.29 ★ 授权 Cookie 挂在**兄弟子域**上：CookieJar 不许按 host 分桶（v1.0.53）

**现象**（huangju.net）：分类、列表、详情、自检**全绿**，一按播放就 `403 MissingKey`；
同一个地址在浏览器里播得好好的。这类"只有播放挂"的现象最容易被归到播放器 / HLS 上去。

**真因**：播放地址由 `video.huangju.net` 提供，授权靠 `/play/{id}` 响应里下发的 CloudFront
签名 Cookie：

```
CloudFront-Policy=…; Domain=.huangju.net; Path=/; Secure; HttpOnly; SameSite=Lax
```

`Domain=.huangju.net`（前导点）是**跨子域**的。而原来的 `CookieJar` 按**请求方的 host** 分桶：
Cookie 是在 `api.huangju.net` 收到的 ⇒ 进了 `api.huangju.net` 那个桶 ⇒ 去
`video.huangju.net` 取 m3u8 / 分片时**永远取不到**。没有异常，只有 403。

**通用机制**：CookieJar **不分桶**，改存一张扁平表（键 `name|domain|path`，让同名 Cookie
挂在不同域下各占一格），发送时一律交给 OkHttp 自己的 `Cookie.matches(url)` —— 它按
`Domain` / `Path` / `hostOnly` / `Secure` 自己判该不该发给这个 URL；顺手把过期的清掉。
"跨子域"从此不再依赖我们记得它。

**顺带确认**：`mediaClient` 与 `client` 共用**同一个** `cookieJar` 实例 ⇒ 播放链自动跟着修好，
不需要第二处改动（"数据源必须与网络栈共用"那条纪律的又一次收益）。

**怎么留痕（不必上机）**：脚本把 `/play/{id}` 的 `Set-Cookie` 收进 jar，再拿 jar 取 m3u8 / 分片：
无 Cookie ⇒ 403，带 Cookie ⇒ 200（`#EXTINF` 198 条 + `#EXT-X-ENDLIST`，分片 `video/mp2t`）。
**对照组就是"不带 Cookie"的那一次**（同 S1：能播不是证据，错的输入也得给出应该有的错）。

### 4.30 ★ 「无论怎么校准都不生效」，有时是**这个站没有形状可学**（v1.0.53）

**现象**（huangju.net）：分类、播放**怎么校准都失败**；但网页上一切正常，进剧集直接开播、
连选集都不用。

**真因**：它是 Next.js App Router（RSC）站，**SSR 出来的 DOM 里没有数据**：
`/theater` 只有 3 个排序 tab，卡片是 `/?drama=…&ep=1` 这种同页 query，`<video>` 连 `src`
都没有（播放地址由 JS 调接口拿到后设上去）。而它的**地址簿不写死在代码里**，运行时从一份
签名配置读：

```
GET {origin}/config.json →
{ "alg": "ed25519",
  "payload":   "<base64 的 {api:[…], seed:[…], track:[…], video:[…], version:N}>",
  "signature": "<Ed25519 签名>" }
```

所以「校准」这件事**方向就错了**：校准学的是**形状**（分类的形状、播放页的形状），
而这站没有形状 —— 分类是接口给的 264 条，播放地址在接口响应里。

**通用机制**：新增一族 `SeedRouter` → `SeedApiAdapter`，判据是**能力自证**：
`alg == ed25519` + 非空 `signature` + `payload` 能解成 JSON 且带**至少一个 http 的 api 地址**。
与它叫什么域名无关（域名会轮换，种子地址还有 jsDelivr / raw.githubusercontent 镜像兜底）——
正是 4.1「会轮换的东西不能当身份」的同一条结论。三层判据都要过才认 ⇒ 对普通站零误判；
这条特别要紧，因为它是**全站兜底路由的第一站**，误判会从"多认一个站"变成"毁掉所有站"
（所以 `runseed.py` 里 13 条反例是主角，见 4.19）。

**还得把话说给用户听**：命中之后 `calibDiag` 直接写明"本站自证为签名种子配置族 ⇒
**校准学不到东西不是校准的问题**"，否则用户会一直在校准页里打转（同 C1 的口径：
五种成因界面看不出区别）。

**接口契约（实测，2026-09-22）**，三个**静默**坑都只体现在数字上，必须写进注释：

| 用途 | 请求 | 静默坑 |
|---|---|---|
| 分类 | `GET {api}/categories` | 返回 `[{id,slug,name}]` 264 条 |
| 列表 | `GET {api}/dramas?page=N&pageSize=M` | `total=1393` |
| 分类筛选 | `…&category={slug}` | 数字 `categoryId=` 被**静默忽略** ⇒ 返回全量 1393 =「点了分类没反应」 |
| 搜索 | `…&q={关键词}` | `keyword=` 同样**静默忽略** ⇒ 返回全量 =「搜什么都一样」（同 S1 形状） |
| 详情 | `GET {api}/dramas/{slug}-{id}` | id 是**两段**（slug + 数字 id 拼起来） |
| 播放 | `GET {api}/play/{episodeId}` | 返回 `{url,expiresAt}` + 授权 Cookie（见 4.29） |

**地址一律相对 `config.json` 给的 api 拼**，一个域名都不写死 —— 这一族的设计意图就是换域名。


### 4.31 ★ 怀疑"是自己改出来的"时：把改动**退回去再跑一遍**（A/B 定位法）（v1.0.53）

v1.0.53 加了最外层路由后，离线回归红了 4 套、联网红了 5 套。13 条 FAIL 摆在面前时最容易做的
两件错事是：**全部归给"站点漂移"**（万一真是回归就漏了），或**全部归给"我改的"**（然后去改没坏的代码）。

本次用的是最省事也最硬的办法 —— **A/B 定位**：

1. 把**被怀疑的那一处**改动临时退回原样（工厂第 ⑤ 步 `SeedRouter(site)` → `FamilyRouter(site)`），
   加一行 `// [AB-EXPERIMENT]` 注释；
2. 只重建 debug（`assembleDebug`，20 秒）；
3. 跑**同一条**断言；
4. 结论只有两种：
   - **退回去也照样红** ⇒ 与本次改动无关（站点漂移 / 环境），把它归到 `NET_SUITES` 或换解释器；
   - **退回去就绿了** ⇒ 真是自己改的，回去看那一处到底删了什么。

本次的原始记录（`runbs3` B 段详情页请求条数）：

| 代码 | A 段请求数（无配方，含回首页现学） | B 段请求数（有配方） | 断言 |
|---|---|---|---|
| v1.0.53（SeedRouter） | 7 | 5 | FAIL |
| 退回 v1.0.52（FamilyRouter） | 6 | 5 | FAIL |

→ 退回去**同样红**（B 段 5 ≠ 1），所以这 2 条是站点漂移；而 A 段 7 vs 6 正好差 1，
就是种子族那一次 `config.json` 探测 —— **新增开销被量出来了，不是猜的**。

**顺带定出的规矩**：`runbs3` 从此归 `NET_SUITES`（它跑 live 站、断言请求条数，
站点多引两个 JS 就会红，而那是站点的事）。

### 4.32 ★ 换了"默认兜底"之后，旧兜底层的规矩会**跟着被删掉**（v1.0.53）

`AdapterFactory` 的第 ⑤ 步原来是：

```kotlin
val famAbsent = fam is CryptFamily.State.Absent
return if (famAbsent) HtmlAdapter(site) else FamilyRouter(site)   // 「Absent ⇒ 零成本」是 v1.0.35 定的
```

v1.0.53 要在这里插一层 `SeedRouter`，先把工厂退回 `FamilyRouter` 做了个 A/B，
**恢复时只写回了 `return SeedRouter(site)`** —— 上面那行 `Absent` 判断连同它的规矩一起消失了。
症状：编译绿、功能照常、离线断言只红了 3 条看着像"位置守卫过时"的。

**为什么危险**：这类丢失**不改变任何可观察行为**（`CryptFamily.resolve` 本来就有磁盘缓存，
包的层数只影响对象图），所以"跑一遍看看"永远发现不了。**只有源码守卫能发现**（`Family.java` D4）。
这就是"既有规则必须有行为/源码断言兜住"（C6）那条纪律存在的理由。

**修法不是删守卫，是让守卫跟着规则走**：规则从"工厂里有 Absent 分支"变成
"工厂把 Absent 传下去 + 路由据此落到 `HtmlAdapter`"，于是 D2/D3/D4 三条都改成**跨文件判语义**：

```kotlin
// 工厂：把否定结论传下去
return if (fam is CryptFamily.State.Absent) SeedRouter(site, familyAbsent = true)
       else SeedRouter(site)

// 路由：据此选落点（Absent 只说明它**不是加密族**，种子族是另一个族 ⇒ 那一层探测仍然要跑）
private val fallback: SiteAdapter by lazy {
    if (familyAbsent) HtmlAdapter(site) else FamilyRouter(site)
}
```

**通用动作**（下次要替换/插入一层时照做）：先把被替换那几行**逐条读一遍**，
列出它承载的每一条规则（这里是"Absent 零成本"），确认每条都有新的落点，再动手。

### 4.33 ★ 「名字叫签名」不等于「验过签」：名实不符本身就是一笔债（v1.0.53）

`SeedConfig` 的判据是：`alg == "ed25519"` + `signature` 非空 + `payload` 解得开。
**它从头到尾没有验签** —— 而且这是**刻意不做的**，不是漏做：

- 这一族的立意就是「域名会换也要认得」。真验签会在对方轮换密钥时让**全族立刻失效**，
  正好牺牲掉这一族唯一的强项；换来的"安全"在本场景还是空的 —— 我们并不"信任"那个 api，
  只是拿它当适配入口，站点内容终归是对方提供的。
- minSdk 21 的 `java.security` 没有 Ed25519（要 API 33+），要验就得引 BouncyCastle
  或自实现曲线运算。为一个"识别标记"付这份代价不划算。

**问题不在"没验签"，而在"看起来像验过"**：

| 表面 | 读起来 | 实际 |
|---|---|---|
| 字段叫 `signature` | 有密码学含义 | 只用来判**非空** |
| 类注释写"三层判据很紧 ⇒ 不会误判" | 所以是可信的 | 只是"不会认错族"，与"内容可信"无关 |
| 诊断文案「本站**自证**为签名种子配置族」 | 签名验证通过了 | 「自证」在本项目是**能力自证**（解开了信封），与签名无关 |
| `apiBase()` 返回地址被拿去请求 | 是个被担保的地址 | 只是**对方自己在配置里写的一行字** |

**处置（方案 B，零成本，不改行为只把话说准）**：
`SeedConfig` 文件头加「关于 `signature`：它是**识别标记**，不是安全边界」一节；
`ALG` 与 `apiBase()` 的 KDoc 各自点明不验签；
两处诊断文案「自证为」→「识别为（依据：解开 /config.json 的信封）」。

**什么时候才该做方案 A（真验签）**：等这个地址要承载**信任**语义 ——
云端下发配方、用户之间互传配方。**那时候「识别」不够用了，才需要「保证」**
（内置公钥 + 自己的 Ed25519 实现），否则任何人都能伪造一份配置把请求引到任意地址。

**通用动作**：给字段/函数起名、或写诊断文案时，问一句
「**读的人会不会以为它做了它没做的事？**」会 ⇒ 要么当场把话说准，要么真把那件事做掉。
**名字承诺的能力，代码必须兑现** —— 否则将来某个人（很可能是自己）会基于这个名字做出错误推断。

### 4.34 ★ 「把本地 harness 搬进 CI」有四类静默失败：绿是假的，只有红会说话（v1.0.53）

harness 原来住在仓库外的私人工作区，工具链路径全写死 `D:\...` / `C:\Program Files\...`，
**结构上不可能进 CI**。搬迁本身不难，难的是**这次搬迁过程中"看起来对"的中间态特别多**。
四类都实测踩到了（`tools/verify/`，42 套件 / 1791 条断言）：

| # | 现象 | 真因 | 处置 |
|---|---|---|---|
| 1 | 18 个套件 `rc=1`，输出里**一条断言都没有** | 脚本把 `PROJ = "D:\\..."` **就地**换成 `PROJ = _cp.project_root()`，而 `import _cp` 仍插在原来的位置 —— **在使用点之后** ⇒ `NameError` 当场退出 | 不再逐个人工比对：用 AST 找**首个真实代码引用**（跳过文档字符串里提到的 `_cp.classpath()`，那是误报源），删掉散落的 import，在首用处前重插引导行 |
| 2 | 本地全绿，CI 上**必然红** | 只迁移了 `*.py`。`*.java` 里的 `"\\app\\src\\..."` 与绝对默认值原样保留 —— Windows 上跑得好好的，**Linux 上 `\` 是合法文件名字符** ⇒ `Paths.get()` 拿到一个不存在的长文件名，`read()` 返回 null，断言红在"文件读不到"，指向的是错的真因 | 迁移要**按文件类型清点**：`.py` / `.java` / 样本 / 资源。路径拼接一律 `/`（`Paths.get("D:/a/b")` 在 Windows 也成立） |
| 3 | 夹具明明在仓库里，套件仍然"缺样本" | Java 侧的默认值（`static final String DIR = "D:/..."`）在 runner 不传参时**才是**实际入口；改成相对路径后 `dir + "home.html"` 又缺结尾分隔符，拼成了 `_bshome.html` | 两条一起改：**runner 显式传解析后的目录**；Java 侧对传入目录**补分隔符**（裸拼接必须容错）。默认值只留"本机直跑"的兜底作用 |
| 4 | 夹具缺失/只编译不断言，回归也判**通过** | `runall.py` 只数 `[PASS]`：LineFix 打的是裸 `  PASS  `⇒ 15 条被数成 0；且"rc=0 且无 FAIL"就算过，`runsurvey.py` 这种**要 URL 参数的工具**混在套件里只会产出假绿 | 补计裸 `PASS`；**零断言标 `WEAK` 且退出码 1**（"没断言"与"断言通过"必须分开）；把纯工具移出回归列表并在文件头写明理由 |

**通用的三条**：

1. **验收看「断言条数」，不看 rc。** 编译通过、进程 0 退出，和"断言真的跑了"是三件事。
   所以每个套件都要能在汇总里给出 `PASS=n`；`n=0` 一律当作失败。
2. **迁移类改动按「文件类型」清点，不按「改动点」。** 这次漏的正是"另一门语言里的同一件事"
   （`.py` 改了、`.java` 没改）。清单应该是 `*.py` / `*.java` / `*.json` / 样本 / 资源 / CI 配置。
3. **CI 化的唯一判据是「换一台机器还能不能跑」** —— 具体就是
   「没有 D 盘、没有本机 cwd、没有 Windows 分隔符、没有本机装过的包」。
   凡是在本机能过、在别处会挂的东西，都属于**没做完**。

### 4.35 ★ 「本地全绿」不是证据：要**铺一棵只剩已跟踪文件的树**再跑一遍（v1.0.53）

4.34 修完之后本机 42 套件全绿。但那一刻**仍然不知道 CI 会不会绿** —— 因为本机多出来的东西
（工程根的 `_bs/`、`_s3~_s6/`、抓下来的 `_*.html`、`app/build/` 产物）**恰好是缺了会红的那些**。
"本地绿"只证明了"在我这台机器上绿"。

**做法（已固化成 `tools/verify/ci_sim.py`）**：

```bash
git archive --format=zip -o %TEMP%/ci.zip HEAD     # 只要已跟踪文件 = CI checkout 的内容
# 解到临时目录后，补两样 CI 上由 gradle 现造、本地靠副作用存在的东西：
#   app/build/tmp/kotlin-classes/  +  .../R.jar  （CI 上是 Build APKs 那步产出的）
#   local.properties             （CI 上由 ANDROID_HOME 顶替）
python tools/verify/ci_sim.py                      # 在那棵树里跑 runall.py，rc 与它一致
```

**为什么值得单独做一步**：`git archive` 与 `git status` 的差别，正好就是"入仓了没有"。
本地随手抓起的一份样本、一个被 `.gitignore` 挡掉的产物，在这棵树上**不存在** —— 于是
"某个套件其实一直在读一个没入仓的文件"这类问题会在**推之前**暴露，而不是在 CI 日志里。

**边界**：它只能证明"**文件**层面等价"，证明不了平台差异（Linux 的 `\`、大小写敏感、
没有 `local.properties`）。平台差异要靠 4.34 第 2/3 条那种**静态清理**来保证；
两者一起才等于"CI 会绿"。这台机器上依然是 Windows，所以 `\\` 类问题不会被它抓到。

### 4.36 ★ 接进 CI 后的第一次红，多半是**分类**错误而不是代码错（v1.0.53）

4.35 的仿真在本机全绿（42 套件 / 1791 条），推上去 CI **照样红**：5 个套件、20 条断言，
清一色是"站点不通"。原因不是代码，是**我把 5 个活体依赖的套件放在了离线列表里**。

**CI 一致性其实有两层，别把第一层当成全部**：

| 层 | 能不能在推之前验 | 靠什么 |
|---|---|---|
| **文件层**：该入仓的东西入了没有 | ✅ 能 | `git archive HEAD` 铺树再跑（§4.35 的 `ci_sim.py`） |
| **网络层**：断言依赖的外部资源，在**runner 的位置**上还在不在 | ❌ 不能 | **只有真 CI 会告诉你**。开发机的出口 IP 与 runner 不同 —— 中文站、带签名短效 CDN 直链，本机通、runner 不通是常态 |

**判据：一个套件该不该进 `NET_SUITES`，只看「它有没有对真实域名发起读请求」。**
两个"看起来更聪明"的静态判据，实测都是错的 —— 记下来，别再走一遍：

- ❌ **"源码里出现了真实域名"** ⇒ 反例 `HdFix2.java` / `LineFix.java`：都写着
  `czzy.app` / `fengbao12.com` 字样的 Referer，但只在**本地夹具**上做文本处理，CI 通过。
- ❌ **"源码里出现了 `Http.INSTANCE` / `newCall` 调用点"** ⇒ 反例 `Agg37.java`：
  有调用点，但走的是未触发的分支，CI 通过。

⇒ 静态分析**判不出来**，所以别去写那个静态守卫（写出来只会得到一堆假红，比漏判更坏）。
改成一个**提示**：`runall.py` 在套件失败时扫日志里的网络痕迹
（`UnknownHost` / `ConnectException` / `SocketTimeout` / `HTTP 403|404|5xx` / "抓取失败"），
命中就多打一行"这套件若不该连外网，应归 `NET_SUITES`"。
**它只给结论，不做裁判** —— 判错的代价是让人多看一眼，判错的代价不是假红。

**这次的正确处理**（5 个全挪，且**本机再跑一遍确认它们仍然通过**）：
`runretry`（`checkSite("茶杯狐"/"厂长资源")`）· `runenc`（CDN 可达性）
· `runhdfix` / `runrank`（读带签名的短效 CDN 直链）· `runextract2`（真抓 `czzy.app` 播放页）。
挪完在**本机**单独跑这 5 个：`PASS=104 FAIL=0` —— 这一步很重要，它是"**是地域网络问题，
不是我们的回归**"的证据；只挪不证，就等于把真回归一起藏进 `NET_SUITES` 了。

### 4.37 ★ 「推上去了」不等于「发版了」：Release 由 tag 触发（v1.0.53）

用户问「我能下载最新版了吗」。一查 Releases，最新还停在 **`v1.0.41`** —— 而代码早已是 1.0.53。
中间的 v1.0.42 ~ v1.0.53 **全是 push main、一次 tag 都没打**。

根因在 workflow 里，不在构建：

```yaml
- name: Publish Release (on tag)
  if: startsWith(github.ref, 'refs/tags/')      # ← 关键：只有 tag 才发布
  uses: softprops/action-gh-release@v2
```

`on: push: branches: [main]` 只负责**构建 + 上传 artifact**（artifact 得登录 GitHub 才能下、有保留期）；
`tags: ['v*']` 才触发**发布**。所以「CI 绿」和「用户下得到」之间隔着一个 **tag**。

**通用教训**：一条流水线里，「构建成功」「上传了产物」「对外发布了」是**三件事**。
只看到前两件绿就以为用户拿得到，又是一次把**进程状态**当成了**结果状态**
（同 §4.34 的 `rc=0` vs 断言数）。**判据必须落到用户那一侧**：
「用户能不能从**他平常下载的入口**拿到**当前版本号**」。

**发版动作（三步，第三步最容易漏）**：
1. bump `versionCode` / `versionName` → 提交 → 推 main（走区间推送工具）；
2. `gh api -X POST repos/<o>/<r>/git/refs -f ref=refs/tags/v<ver> -f sha=<main HEAD>`；
3. 等 tag 那轮 CI，确认发布步骤 success，**并核验 `releases/tags/v<ver>` 里的 asset 列表非空**
   （只看到 release 出现、没看 asset，等于没核）。

签名不需要为 CI 额外配置：`keystore.properties` 在库内 ⇒ CI 的 release 包是**真签名**；
debug 也复用同一把钥匙 ⇒ 覆盖安装不会「应用未安装：签名冲突」。

### 4.38 ★ 「改了代码」≠「包也是新的」：同版本号的两代包（v1.0.53）

回答「你改的 #1#2#3 在 1.0.53 里吗」时顺手验包，发现**四个自称 1.0.53 的 APK 其实是两代**：

| 位置 | 体积 | dex 字节 | #2 新文案 | 旧措辞 |
|---|---|---|---|---|
| Releases（CI 出的，**用户下载到的**） | 8,005,679 | 16,615,800 | ✅ | 已消失 |
| `app/build/.../app-release.apk` | 8,005,682 | 16,615,660 | ❌ | **还在** |
| `releases/VideoShell-1.0.53-release.apk` | 8,005,682 | 16,615,660 | ❌ | **还在** |
| `videoshell-apk/release/app-release.apk` | 8,005,675 | 16,615,660 | ❌ | **还在** |

根因很朴素：#2 改的是 Kotlin **字符串常量**，改完**只提交、没重建**；
而 `versionCode` / `versionName` 在更早的提交里就已经是 53 了。
于是**新旧两代包同名同版本号**，体积只差 3~18 字节 —— 装机、甚至肉眼都分不出来。

**判据：改完 Kotlin 就重建，这不是「为了编译通过」，是「为了让产物跟源码对齐」。**
发版后要**验包**（不是验源码）：

- 在 **dex** 里搜本版**新增**的字符串，并且**旧字符串必须搜不到** —— **两个方向都要查**；
- **必须带对照项**：一个必然存在的串（如 `com.videoshell`）+ 一个必然不存在的串。
  没有对照，一个 `NOT FOUND` 什么都证明不了 —— 分不清「确实没这段文案」和「我这套搜法压根没生效」。
- manifest 的字符串池可能是 **UTF-16**：版本号按 UTF-8 搜会假 `NOT FOUND`，两种编码都要试。

工具：`D:\TRAE\releases\.tools\_apk_scan.py`（逐包扫 + 对照项 + 版本串，可反复用）。

**同一件事的第二面：迁移/改名之后，外围引用要跟着改。**
每日探针的 WorkBuddy 自动化里写的还是**迁移前**的路径
（`D:\TRAE\releases\.tools\videoshell_verify`）与**写死的 6 个**套件名。
harness 搬进仓库后，仓库里的 `runall.py` 已经是 11 个 NET 套件，
但自动化**仍在跑旧目录里的旧副本** —— 它不会报错，只会安静地给出过期结论。
⇒ 迁移类改动的清点范围要包含**编排层**（定时任务 / CI 配置 / 文档里的命令行），
不只是仓库内的文件。这是 §4.34 第 2 条「按文件类型清点」的延伸：**还要按「引用方在哪」清点**。

### 4.39 ★ "本地绿"和"CI 绿"之间还差一层：**夹具可能不是同一份**（v1.0.53）

§4.35 说的是"本机多出来的文件"，这条说的是**同一路径下两份不同的文件**。

`_cp.samples(name)` 是**两处查找**：

```python
cand = os.path.join(project_root(), name)          # ① 工程根 _bs/、_s3~_s6/（未入仓）
if os.path.isdir(cand): return cand                #    ← 优先！
alt  = os.path.join(HERE, 'samples', name.lstrip('_'))   # ② 入仓的 tools/verify/samples/<name>/
if os.path.isdir(alt): return alt
```

设计意图（注释里写了）是"本地跑最新抓的那份、CI 跑入仓的那份"。**代价**：
本地绿 → CI 绿 这条推理链上多了一个**没人检查过的假设**——两份内容一样。

**怎么把假设变成判据：sha1 比一遍。**

这次清理时的实测（`_s6` 例外，见下）：

| 工程根 | 入仓 | 结论 |
|---|---|---|
| `_bs` / `_s3` / `_s4` / `_s5` | `samples/{bs,s3,s4,s5}` | **逐字节相同**（sha1 全等）⇒ 纯副本 |
| `_s6` | `samples/s6` | `cf_doctor_v6.txt` / `cz_doctor_v6.txt` **不同** |

删掉那 4 份纯副本后本地回归 **37 套件 / PASS=1687 / FAIL=0** —— 这同时证明了
"入仓夹具是完备的"（与 CI 的结论一致），而不是"本地那 4 份有多余价值"。

**`_s6` 为什么必须留**：它那 2 个文件的 **mtime 是当天**（其余 3 个是几天前）⇒
有套件**往这个目录里写**。而 `samples/*` 是入仓夹具、`_s6` 是未入仓的 scratch：

- 留着 `_s6` ⇒ 写入落在未入仓目录，**工作区始终干净**；
- 删掉 `_s6` ⇒ `samples('_s6')` 回落到**入仓**目录，写入会直接改到被跟踪的文件上，
  **每天跑一次回归就把工作区写脏一次**。

反过来这也解释了为什么那 4 份是"逐字节相同"的：**没有东西写它们，所以它们从没分叉过**。
⇒ **一条便宜的判据：mtime 有没有分叉。** 分叉过 = 有人写它 = 它不只是副本。

**通用动作**：判"这个样本目录是不是纯冗余"时不要看名字像不像垃圾，看两件事 ——
① **sha1 是否与权威副本全等**（是 ⇒ 内容上可删）；
② **mtime 是否分叉过**（是 ⇒ 它是 scratch，删了会把写入引到被跟踪的文件上）。
两条都过了才叫"可以删"。

### 4.41 ★ 拆 god file（纯搬运）之所以能"与守卫无关"，靠的是**两层**机制（v1.0.54）

把 1700 行的 god file 按职责拆成几个文件，本身一行逻辑都不改 —— 但守卫是**读源码文本**做
`contains` / `body_of` / `count()==N` 的，路径和函数签名一变就会满地假红。让"搬运"对守卫不可见的
是两层机制，缺一层都会红一片：

**第一层：聚合读取（`<主名>.kt` + `<主名>_*.kt`）**。把「某个类的全部源码」定义成
「主文件 + 同主名的拆分子文件」，守卫的路径就不再绑死文件布局。见 `tools/verify/_cp.py` 的 `kt()`
与 8 个 Java 守卫里的 `agg()`（两份实现必须**同时**改，只改一边的症状是"Java 套件红、Python 套件绿"）。
纪律：拼接**不复制内容** ⇒ `count(x) == 1` 这类"只此一处"的计数断言语义不变。

**第二层：恒等还原（`unwrap`）**。子文件里被搬走的函数一律是
`internal fun Owner.xxx(`（扩展函数访问不了 `private`），而判据写的是 `private fun xxx(`。
`unwrap` 按行做 1:1 改写把签名还原成类成员写法，让聚合文本与拆分前**逐行等价**。
1:1 替换不复制不删除 ⇒ 真被删掉的代码不会因为改写而"看起来还在"。

**同一个坑踩了四次，全是"名字对得上、正则认不出"**（表现为"每轮都放宽 0 处，错误却一直在"）：

| 次数 | 声明形态 | 正则缺什么 | 症状 |
|---|---|---|---|
| 1 | `private var` / `private lateinit var` | 只写了 `private val` | 每轮 0 处 |
| 2 | `private suspend fun` | 漏 `suspend ` | 每轮 0 处 |
| 3 | `private data class Card`（**嵌套类型**） | 认不出 `class` | 每轮 0 处 |
| 4 | `private inner class Bridge` | 漏 `inner ` | 每轮 0 处 |

⇒ 写这类"自动修"脚本时，**必须**同时具备"声明形态全覆盖"与"零改动就停下喊"两条。
只报"处理了 0 处"而不停，看起来在干活、实际一个字没改 —— 与 §4.34 的"绿是假的"同型。

**编译器报错的四种措辞都要认**（同一件事：谁看得见谁）：
1. `Cannot access 'x': it is private in 'Owner'`（成员 private）；
2. `Cannot access 'x': it is private in file`（**顶层** private，报错里**不带**所有者类名 ⇒ 只能按声明名反查文件）；
3. `'internal' function exposes its 'private-in-class' return type Card`（不是"访问不到"，是**泄露**）；
   ——注意备选顺序必须长的在前：`return type argument` 写在 `return type` 后面时，
   会被 `return type` 先命中，剩下的 ` argument X` 被当成名字捕获成 `argument`。
4. 同一函数被搬到子文件后，`owner` 类名在报错里仍是**所有者类名而不是文件名** ⇒ 找声明要去
   `Owner.kt` **和** `Owner_*.kt` 两处（`LineBlock` / `Card` 就住在子文件里）。

### 4.42 ★ 纯搬运拆分的五条硬约束（每条都踩过，且两条是**静默**的）（v1.0.54）

**① `override fun` 一个都不能搬**。扩展函数不能覆盖成员 —— 搬走等于把生命周期回调整个删掉。
区间上下界就是照着 `onCreate` / `onBackPressed` / `onStop` / `onDestroy` / `finish` 切的
（CalibrateActivity 的 Web 组止于 427、下一段起于 433，中间夹的正是 `onBackPressed`）。

**② `this@Owner` 在扩展函数里不成立 —— 而且 `this` 也不能拿来顶替。**
隐式接收者的标签是**函数名**：`this@Owner` ⇒ 必须改写成 `this@函数名`。
不要图省事换成 `this`：SniffActivity.recognizeAndAdd 里那 3 处全在
`lifecycleScope.launch { … }` 内，那里的 `this` 已经是协程作用域了。
（PlayerActivity 当初是加 `val self = this` 绕过去的，两种写法都对；关键是**不能不管**。）

**③ 静默的一类：private 字段的名字撞上**继承自父类的属性** ⇒ 编译器不报"访问不到"，改用父类那个。**
SniffActivity 的 `private var title: String` 撞 `Activity.getTitle(): CharSequence!`：
类内子类字段遮蔽父类属性 ⇒ 取到 `String`；搬到扩展函数后 private 字段看不见了，
Kotlin **不报错**，改用父类的 `title`（`CharSequence`）。表现是
`Type mismatch: inferred type is CharSequence! but String was expected` —— 这还算幸运的。
**更坏的情况**：那一处本来就收 `CharSequence`，于是静默变成"Activity 的标题"，行为已经变了而编译全绿。

⇒ 结论：**只靠编译错误驱动的自动修可见性，看不见这一类**。必须在编译**之前**做一遍
**按引用静态放宽**：凡是拆分子文件里出现过的标识符，只要主文件里是 private 类级声明，就先放宽。
（`_fixvis.py` 的 `static_widen()`。放宽可见性不改行为，多放宽几个只是难看。）
判据：**"编译绿"只证明没有硬冲突，不证明名字解析没换对象**。

**④ 嵌套类型不会自动进入别的文件的作用域**：`Pick` / `NavPick` / `Card` / `LineBlock` 被写进
扩展函数的签名后，顶层作用域解析不到 ⇒ `Unresolved reference: Pick`。
两条出路：`_spec` 头部手写 `import <包>.<Owner>.<类型>`，或让收尾脚本
（`_fixvis.py` 的 `nested_types()` 分支）自动补 —— 后者更可靠，因为**不依赖人记住**。
另外 `companion object` 的成员**不能**用 import 解决：类外必须写 `Owner.MODE_XXX`（语法要求），
所以由收尾脚本在调用点补限定名。

**⑤ 顺带一条判据纪律**：上面 ④ 的限定名会让守卫里写的裸名（`mode == MODE_SEARCH`）失配 ——
那是**位置**变了、不是行为变了，处理方式与"判据不带 `private ` 前缀"（§4.24）完全一样：
在比较前把 `Owner.` 剥掉（`runui40.py` / `runui50.py` 里的 `unqual()`），**不要**把代码改回去。

### 4.43 ★ 把私钥放进仓库 = **不可逆**的操作；「重写历史」并不能撤销它（v1.0.54）

本工程的 `keystore/videoshell.jks` 与 `keystore.properties`（**含明文口令**）从根提交 `c68c93a`
起就是被跟踪文件，59 个提交全带着它。仓库从 private 转 public 的那一刻，签名私钥就公开了：
任何人都能签一个 `versionCode` 更大的同名包，而 Android **只认签名** —— 用户装了它，就等于
把「更新」交到别人手里（自更新功能会把这件事放大：它主动去下载并提示安装）。

**最容易算错的一步**：以为"删掉文件 + 重写历史 + force push"就干净了。
**不是。** GitHub 上不可达对象**按 SHA 仍可取到**（要等后端 GC，而它不保证发生）。
所以只有两条真正有效的路：

| 方案 | 私钥是否真的清掉 | 存量安装能否覆盖升级 | 代价 |
|---|---|---|---|
| **换新钥匙**（本项目选的） | ✅ 旧钥作废，新钥只在 Secrets / 仓库外 | ❌ 必须**卸载重装**一次 | 最小，且是唯一能立刻做成的 |
| **删库重建**（同名） | ✅ 旧对象随之消失 | ✅ 继续用同一把钥匙 | star / issue / Release 记录清零，CI secret 与连接器要重配、tag 要重打 |

选完之后的动作（本项目已落地的形态）：

1. 新钥落在**仓库外**（`../releases/.keys/videoshell.jks`），`keystore.properties` 指向它并进 `.gitignore`；
2. 四个值进 GitHub Secrets：`VS_KEYSTORE_B64` / `VS_STORE_PASSWORD` / `VS_KEY_ALIAS` / `VS_KEY_PASSWORD`；
3. `git rm --cached` 掉两个文件，并加一条 `keystore/README.md` 说明"密钥不在这里、旧钥已作废"
   —— 公开仓库里最容易被后来者误当成"忘了提交"；
4. CI 里 `base64 -d` 解到 **`$RUNNER_TEMP/sign/`**，**刻意不放工作区**：放工作区会被
   `actions/upload-artifact` 打包上传，等于换个地方再泄一次。解完立刻 `keytool -list` 自证，
   这一步红比"签名悄悄没了、包却照样发出去"好得多；
5. `app/build.gradle` 签名**优先读环境变量**，其次本地 properties ⇒ 本机与 CI 都能出真签名包。
   **debug 也用 release 钥匙**：默认 debug 走调试密钥，会与 release 互相覆盖安装失败，
   症状是「我明明装了新版，界面还是老的」—— 任何代码排查都解释不通。

**发布前检查清单（转 public / 发版各一次）**
`git ls-files | grep -iE 'keystore|\.jks|\.properties'` 的结果里**不能**有密钥材料；
CI 产物里不能出现 `*.jks`（`upload-artifact` 的 path 要覆盖到 `$RUNNER_TEMP` **之外**才行）。

**⚠️ 换钥与「自更新」撞在一起的连招**（本项目实发 v1.0.54 时确认）：
自更新是**检查 → 下载 → 交给系统安装**，而系统在安装阶段才校签名。于是老钥装的存量 App
走 self-update 会**下载成功、sha256 校验通过、然后在安装那一步失败**（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）。
也就是说 —— **"跨换钥"这一次升级，自更新机制帮不上忙，只能手动卸载重装**。
凡是"换钥"与"加自更新"发生在同一个版本，都要在 Release notes 里**明说这一条**，
否则用户看到的现象是"它下载完了却什么都没发生"，而日志里只有一条容易被忽略的安装失败。

**转 public 之后的历史取证面**：旧钥仍躺在 `c68c93a` 起的历史里（`git show` 就能取出），
这在选"换新钥匙"时是**已知且接受**的代价 —— 之所以可接受，是因为旧钥同时作废了：
拿旧钥签的包**装不到新钥签的 App 上**，只能骗还没升级的存量用户，而那部分用户本来就在用旧钥。
真正要守的是**新钥**：它一旦再进仓库，下次就没有"作废"这个选项了（存量会越来越多）。

### 4.44 ★ 「更新清单」必须和「包」在**同一个** Release，且版本号从 **APK** 里读（v1.0.54）

应用内自更新读的是 `releases/latest/download/version.json`。两个坑：

1. **清单与 APK 分两次上传** ⇒ 会出现"清单已更新、包还是旧的"的窗口，而且它**不报错**：
   用户点更新，装到的还是老版本。所以两者必须由同一个 job 在同一次 `action-gh-release` 里发布。
2. **版本号必须从 APK 里读**（`aapt dump badging` 优先），不能从 `build.gradle` 或 tag 里读。
   源码里的版本号与**真正打进包里**的版本号是两件事（§4.38：同版本号的两代包就是这么来的）。
   并且要**硬校验 `tag` 与 APK 的 `versionName` 一致，不一致就拒绝生成** —— 宁可不发，
   也不要发一个"清单说 1.0.55、包里其实是 1.0.54"的更新。

清单里的 `apkUrl` 指向 `releases/download/<tag>/<apk>`，所以**只在 tag 上生成**；
在 main 上生成没有意义（那时还没有对应的 Release）。
另外：仓库是 private 时，`releases/download/...` 的裸链接对未认证请求返回 404 ——
那是"没权限"不是"没发出去"；判断发没发出去要用 `gh release view`。

### 4.45 ★ 「校准有没有生效」只能看**决策**，不能看**结果**（v1.0.54）

用户问「检查校准模式是否真的生效」。第一反应是去跑 `CalibLive` 的配方矩阵 —— 它列出 10 份配方
（空配方 / 只学分类 / 只学详情 / 三步全 / **故意把 `/bspvd/{id}.html` 改成 `/bspvs/`** …），
每份都走一遍「分类 → 列表 → 详情」。

结果是：**10 份配方打出来的结论一模一样，全部 `OK 4 线路 / 56 集`** —— 包括那份故意写坏的。

这**不能**读成"校准没用"，也**不能**读成"校准有用"：这张表对"配方到底有没有被用上"根本不敏感。
它只观测结果，而结果对决策是**多对一**的。`SiteAdapter` 的注释里其实早就写明了四种可能：

1. 校准没写盘；
2. 写盘了，但本站命中加密白名单 ⇒ 规则被**按设计**跳过；
3. 写盘且生效了，但形状在本页**只命中 1 个**（判据要求 ≥2）⇒ **静默退回**默认逻辑；
4. **生效了**，只是"结果恰好一样"。

只靠"界面看着没变"永远分不出这四种。**判据必须打在适配器自报的决策上**
（`calibApplied` / `calibDiag`，就是自检报告 `[2a]` 那一栏）。给矩阵加一列之后，答案立刻确定：

| 配方 | 校准校验 | 详情 |
|---|---|---|
| 空配方 | 没走校准（正常） | OK |
| `catTpl + navSel`（第 1 步学到） | **生效**（形状命中 42 个，比默认判据的 40 还多 2） | OK |
| 只有 `detailTpl` / `playTpl` | 无分类规则（正常：第 1 步没学） | OK |
| 三步全 | **生效** | OK |
| **坏 `detailTpl`** | 无分类规则 | OK ← **但配方是错的** |

**分类步确实生效。** 而最后一行暴露了详情步的真问题：

**详情步此前是唯一没有任何观测的一步。** 分类有 `calibOutcome`、搜索有 `searchTplSwap`，
详情什么都没有 —— 而 `detail()` 的候选链是「配方模板 → 学到的 → 回首页现学 → 穷举 → 播放页兜底」，
**任何一条成功都算成功**。于是"用户校准的详情形状是错的"与"校准压根没生效"在结果上**完全一样**。

用 `-v` 打出完整 `calibDiag` 才看清机制：坏模板那一次，成功路径是第 1.5 步
「详情页 DOM 里有分集链接 ⇒ 直接去播放页」。而这条路径**直接 return、不写回配方** ——
所以那条错模板会**永远留在配方里**，每次进详情页都要先白发一次请求、再失败一次，
而用户全程看不到任何异常。

**修法（v1.0.54 落地）**：

- 新增 `detailTplOutcome`：配方模板这次**用上了** / **没用上（已改用兜底）**；
- 新增 `detailTplSwap`：配方模板被成功者**替换**时留痕（与 v1.0.33 给 `searchTpl` 加的那条同型，
  当时只做了搜索那一处）；
- 两者都拼进 `calibDiag`，并加 `E11`/`E12` 两条源码守卫 —— 其中 `E12` 专门锁
  **「字段加了但没拼进 diag」**这种加了一半的改法（否则界面上照旧看不见）。

**可迁移的纪律**：判"某机制有没有生效"时，先问一句 **"我现在看到的这个证据，能区分开几件事？"**
只能观测结果、观测不到决策的时候，「全绿」什么都说明不了 —— 这与本项目 §4.31 的 A/B 定位法、
以及"守卫必须带对照组"是同一件事。

### 4.46 ★ URL 去广告的**边界**：实测一页 55 条子资源、判据命中 0 条（v1.0.54）

用户报「网页嗅探时去广告不彻底，广告仍然很多」。先做测量，不先改判据 ——
新工具 `tools/verify/runadbprobe.py <pageUrl>` 把真实页面的子资源逐条喂给**真判据**
（`_cp.classpath()` 加载真编译产物，不是照着源码另写一遍）。

实测（`https://www.bolyship.com` 首页，99330 字）：

| 指标 | 值 |
|---|---|
| 标签属性里的子资源 | 55 条 |
| 判据拦下 | **0 条** |
| 第三方主机 | 5 个，**全是图片 CDN**（`pic.ry-pic.com` 34 条、`pic.youkupic.com`、`hhmage.com`、`img.guangsuimage.com`、`ry-pic.com`） |
| iframe | **0 个** |
| 源码里（含内联 JS）出现的广告/统计域名 | 只有 `v1.cnzz.com` 1 处 —— 而它**被判据拦下了** ✅ |

**所以这不是 bug，是判据的边界。** 这套 URL 判据能做的只有"拦掉域名本身就是广告/统计服务的资源"
和"整段等于广告词的路径"。而真实中文站的广告主体是另外三类，**它们在 URL 形状上与正文没有区别**：

1. **同域广告位**（站点自己的 banner 图放在 `/uploads/…`，链接跳自家 `/ad/`）——
   拦任何一条都会连正文图一起拦；
2. **图片广告**（`/uploads/ads/banner.jpg` vs 一张封面图：形状相同，无法判）；
3. **运行时 JS 注入的 DOM 浮层**（插屏 / 底部下载条 / 遮罩）—— 它不在初始 HTML 里，
   `shouldInterceptRequest` 只能看到脚本本身，看不到它造出来的 DOM。

要真正改善，只有两条路，且**都必须承认误伤**：

| 方案 | 代价 | 前置条件 |
|---|---|---|
| DOM 启发式隐藏（按 class/id 词 + 尺寸/位置） | 会连正文容器一起藏 ⇒ 用户点不到东西；这正是 `AdBlock` 三条自我约束里**刻意拒绝**的事 | 必须：可关、留痕（进 `NetLog`/报告）、且带**反例断言**（"不许藏正文容器"）；先在一批真实页面上量出误伤率 |
| 用户自定义规则 / 订阅 | 需要 UI 与存储；规则错了由用户自己负责 | 判据层要能接受外部输入（参考 `RecipeTransfer` 的"外部输入不带信任"） |

**做这张表之前必须先有数据**：`runadbprobe.py <pageUrl>` 的输出（第三方主机清单 + 漏拦候选）
就是"该加什么"的唯一依据 —— 没有它去加 `AD_HOSTS`，等于照着印象改判据。

⚠️ 这个工具是**诊断工具**（只输出清单、不产生 PASS/FAIL），所以它不进 `SUITES`
（零断言会被标 `WEAK`），也不进 `NET_SUITES`（那一列是给"有断言但依赖真网络"的套件用的）。
它登记在 `runall.py` 顶部的「不在回归列表里的『工具』」一节 —— **不登记就会有人以为它跑过了**。

### 4.47 ★ 「零断言 ⇒ 失败」挡不住**部分跳过**：PASS 数会自己漂（v1.0.54）

这一条是被上一条**顺带**抓出来的。做 §4.45 时对比了两次全量回归的逐套件 PASS 数：

| 套件 | 第一次 | 第二次 | 说明 |
|---|---|---|---|
| `runygimage` | 34 | 36 | +2 = 我新加的 E11/E12（预期内） |
| `runepname` | **48** | **41** | **-7**，两次都报 `OK  FAIL=0` ★ |

`runepname` 在 `SUITES`（离线列）里，但它带一段需要真网络的 **F 段**（`EpName.java` 有两处
`[SKIP] F 段…`，分别对应"自证没命中"和"真网络不可用"）。网络一抖，**7 条断言无声消失**，
套件照样绿。

**为什么原来的机制挡不住**：`runall.py` 只判 `PASS==0 && FAIL==0 && rc==0 ⇒ WEAK`。
那是"整个套件没跑"的守卫；而这里是"套件跑了、但少了 7 条"。部分跳过在日志里
**只表现为一个更小的数字** —— 不去手动逐套件对比，看不出来。这正是本项目自己
写过的"真回归被藏起来"。

**修法（两处，都很小）**：

1. `runall.py` 把每套件的 `[SKIP]` 计数打进该行（`SKIP=n`），并在合计里单列
   `SKIP段=`，有跳过时多打一行说明是哪些套件、跳了几段 —— 让人一眼看出
   "这次 PASS 少是因为跳了段"，而不是"断言被删了"。
2. `runall.py` 头部补第三类**混合套件**（离线主体 + 一小段活体）并写明：
   它**留在 SUITES**，因为离线部分必须在 CI 上跑；**不要**为了数字稳定把它整体挪进
   `NET_SUITES` —— 那等于把它的离线断言从 CI 上摘掉。

**通用教训**：守卫的粒度要跟"覆盖"的粒度对齐。`SKIP` 是一个**覆盖**信号，不是**结果**信号；
只统计 PASS/FAIL 的汇总表，天生看不见"这次少测了哪些"。凡是允许部分跳过的套件，
都必须把跳过数打进汇总 —— 否则"绿"这个字就同时代表了两种完全不同的状态。

### 4.53 R8 × Gson 全灭（v1.0.58，E30）：TypeToken 匿名子类的签名被剥，数据静默清零

**现象**（v1.0.57 → 1.0.58 用户报告，三症一根）：升级后①已有站源列表异常；
②导入此前导出的站源 .json 报「该文件里没有可识别的站点」；③添加新网址后
列表里不出现。**全程零崩溃、零报错** —— 与 §4.52 里警告过的"Gson 静默清零"
完全同形，只是清零的不是字段名，是**类型**。

**根因链**：

1. v1.0.57 首开 R8。`proguard-rules.pro` keep 了 6 个 Gson **模型类**（字段名
   完好，dex 里逐一验过），但漏了另一头：`object : TypeToken<MutableList<SiteConfig>>() {}`
   这类**匿名子类**。
2. Gson 泛型解析的类型**唯一**来自匿名子类的 `Signature` 注解
   （`getGenericSuperclass()`）。gson **2.10.1 的 jar 里没有 consumer 规则**
   （2.11 才加），没有任何东西拦住 R8 把这些未被 keep 的类的 Signature
   **整条剥掉**。
3. `-keepattributes Signature` 只保证"属性不被全局剥"，保证不了"未被 keep
   的类还带着属性" —— 这行给了假安全感。
4. 签名一丢 ⇒ `getGenericSuperclass()` 拿到裸 Class ⇒ `fromJson` 退化为
   LinkedTreeMap / 抛异常 ⇒ `Store.sites()` 的 `runCatching` 吞掉返回空列表、
   `importLauncher` 同理报"没有可识别的站点"、`Store.addSite` 存进去的下一次
   读不回来。

**A/B 对照（判"混淆生效"必须带这一手）**：v1.0.57 与 v1.0.58 的 release dex
按片段核对 —— `Lcom/google/gson/reflect/TypeToken<` 这个 Signature 片段
**57 缺、58 有**；58 与 57 的片段差集里同时多出 `*>;` / `>;>;`（Map/List
签名的收尾片段）。keep 规则加上后片段回来了，判据闭合。

**⚠️ 判据写法上的二次坑（当天就踩）**：DEX 把 Signature 注解值**拆成多个
字符串片段**存储（`Lcom/google/gson/reflect/TypeToken<`、`Ljava/util/List<`、
`>;` 各自独立入池）。拿完整签名串去 dex 里搜**永远 GONE** —— 会把好的
误判成坏的。第一次核验就这么把"57 坏"错判成"探针写错"，绕了一圈才用
debug/57/58 三方片段对比锁死。正确姿势见 `tools/verify/rundexsig.py`
（自带 dex 字符串池解析器）。

**修复与防复发**：

- `proguard-rules.pro`：`-keep class * extends com.google.gson.reflect.TypeToken { *; }`
  （+ TypeToken 本尊）。费用可忽略（十来个几十字节的匿名类）。
- 新套件 `runr8`（13 条，源码层）：开关状态必须"有人知道地改"；keep 清单
  逐条在位；**源码 Gson 调用点 ↔ keep 清单对账**（新增 `fromJson` 目标不在
  清单里就 FAIL）。
- 新套件 `rundexsig`（17 条，构建产物层）：dex 片段级断言，debug↔release
  A/B 对照内建。

**通用教训**：Gson 的 keep 是**两头**的事 —— 模型类一头（字段名 = JSON 键），
TypeToken 匿名子类一头（泛型签名 = 解析目标类型）。只 keep 一头，另一头
静默坏。凡是"反射读类元数据"的库（Gson/Room/Jackson），开 R8 时都要问一句：
**它读的元数据在不在被 keep 的那部分里？** 另外：验"混淆生效"的三件套
（mapping.txt / 体积 / dex 字符串）对"签名被剥"这类损伤**全部失明** ——
三件套验的是"R8 跑了"，不是"Gson 还活着"；跨包 A/B 片段对照才是对的探针。

## §4.48 自更新：清单链上的主机是**间歇可达**的，单通道 = 随机失效

**现象**：点「检查更新」时好时坏。坏的时候只报一句"取不到清单"，而清单内容、URL、
sha256、`parse()` 判据**全都是对的** —— 读代码读不出任何问题。

**根因**（2026-09-22 同机同刻的对照数据）：

| 主机 | 第一次测 | 15 分钟后再测 |
|---|---|---|
| `github.com:443` | **连接超时**（5s 打不通，连续两次） | 8/8 通，各 0.12s |
| `api.github.com:443` | 0.30s ✅ | 8/8 通，各 0.12s |
| `objects.githubusercontent.com:443` | 0.24s ✅ | — |
| `release-assets.githubusercontent.com:443` | 0.36s ✅ | — |

也就是说它**不是恒断，是间歇**。而 `MANIFEST_URL` 的第一跳恰好就是 `github.com`
（`.../releases/latest/download/version.json` 与 APK 裸链都要先过它）——
于是"平时能用、偶尔全废"，且**没有任何日志能指向它**。

**修法**：清单与下载都改成**两条通道**，api 优先、裸链兜底。

| 通道 | 地址 | 取包内容时必须带 |
|---|---|---|
| ① `api.github.com` | `repos/<r>/releases/latest`（JSON 给 assets） | 资产地址要 `Accept: application/octet-stream` |
| ② `github.com` | `releases/latest/download/version.json` | 无（302 直达 CDN） |

⚠️ 那个 `Accept` **不能省**：不带它，`api.github.com/.../releases/assets/<id>` 返回的是
**资产的 JSON 元数据**（几百字节），于是"apk"下下来是个文本，而报出来的原因是
"摘要校验失败" —— 排查方向直接跑偏。

**顺带白得一道校验**：api 通道给的 assets 里带 GitHub 自己算的 `digest`，
它与清单里的 `sha256` 是**两个独立来源**。两者必须相等，否则说明"清单指向的包"
和"这个 Release 里的包"不是同一个 —— 这正是 §4.44 想要的"同一次发布"耦合，
现在多了一条不依赖我们自己 CI 的证据。

**方法论（比这条坑本身重要）**：

1. **"每条规则都成立、组合起来却不可用"只能靠对照实验发现。** 这次是
   `runupdlive.py` 立的功 —— 它同时跑两条路：`A` 直打裸链（对照组）、
   `B` 走 `check()`（实验组）。**只有 A 红 B 绿才能证明改的通道是必要的**；
   两边都绿说明当时网络本来就通、这次只是兜底；两边都红说明还有别的问题。
   造这个 harness 的时候 A 恰好通了（15 分钟前它超时）—— 如果按"跑一次就下结论"
   的习惯，我会得出**"这次改动不必要"的错误结论**。**间歇性故障必须测多次**。
2. **网络类故障要报"试过哪些主机"**，不能只说"失败"。用户唯一有效的动作
   （换网络 / 挂代理）取决于这话说不说得出来。
3. **它不进 `SUITES`**（要网络），**也不进 `NET_SUITES`**（那一列是"有断言但依赖
   真网络"的套件；这个是排查工具，不产生 PASS/FAIL）。它登记在 `runall.py` 头部的
   「不在回归列表里的『工具』」一节 —— 不登记就会有人以为它跑过了。
4. 取而代之进 `SUITES` 的是纯离线源码守卫 `runupd`（17 条）：锁"两条通道都在"、
   "api 在前"、"取内容带 octet-stream"、"白名单仍是 `host == it || host.endsWith(".$it")`"
   （改宽成 `endsWith(it)` 会让 `evilgithub.com` 过关，而没人会去试这个域名）。

### 4.49 ★ 自更新高速镜像层：**"HTTP 200"不等于"给的是文件"**（v1.0.56）

用户要"给热更新加可用的高速代理"。先实测（两次独立测量，`runmirrorprobe.py` 可随时复跑）：
直连 `github.com` 下 APK 只有 **74 KB/s**（8 MB ≈ 110 秒，第二轮直接整段超时），而公共
前缀反代镜像 1000~1900 KB/s（5 秒）—— 差距 **25 倍**。这不是可达性问题，是国际出口
带宽问题，"换网络再试"救不了。

**设计（`UpdateMirror.kt`，三条安全不变量）**：

1. **镜像只搬字节，不扩展信任。** 清单（sha256 的来源）优先 GitHub 本尊；镜像通道取清单
   必须 **≥2 个独立镜像内容一致** 才接受（`viaMirrors`），单镜像应答 ⇒ 拒绝并说明。
   镜像主机**不进** `ALLOWED_HOSTS` —— 白名单判"剥掉镜像前缀后的内层主机"
   （`UpdateMirror.innerOf(url) ?: url`），`wrap(镜像, https://evil.com/x.apk)` 照样被拒。
2. **下载前探测必须验 ZIP 魔数。** ★ 本条是这次真正的新知识：实测 `ghps.cc`、
   `gh-proxy.net` 对**任何**地址都返回 **`200 + 自己的 HTML 页面`** —— 状态码、耗时
   全部正常，字节数不对。只看 HTTP 状态码，它们反而是"最快的线路"；不验魔数，
   整个测速就是在给说谎者排名，最后废在 sha256 上。判据：APK 前 4 字节必须是
   `PK\x03\x04`（ZIP 本地文件头）—— 这是唯一能在**浪费整次下载之前**识破它的东西。
3. **sha256 校验必须在候选循环之内**（顺手修掉 v1.0.55 的一个真 bug）：旧版校验在
   循环外，说谎镜像耗掉唯一一次校验机会后整个更新直接失败；正确行为是
   "该候选作废，换下一个"。`runupd` U15 / `runupdmirror` M20 锁住这条。

**候选顺序由实测决定**：10 条候选（直连 2 + 镜像 8）并发发 `Range: bytes=0-131071`
探测，按 KB/s 排序（`UpdateMirror.rank`，没测出的保持原序垫底 —— 直连是镜像全灭时
唯一确定的退路）。探测失败 ≠ 淘汰：只是没进测速表，整包仍可能下得动。

**镜像清单只在"前两层都失败"时试**，且每个镜像**只试一次**（`Http.getOnce`，
新公开方法）：`get` 的 3 次重试 × 8 镜像 × 超时 = 两分钟假死，"点了没反应"比失败更糟。

**端到端验证（`runupdlive.py` 加 C 组）**：用 App 自己的 Http 走镜像链路 ——
前 2 个镜像返回的清单 sha256 与 api 通道**完全一致** ⇒ 双源一致达成。只靠 Python
探测说"镜像能行"不算数，要用同一套代码走一遍。

守卫：`runupdmirror`（22 条 = 行为断言走真编译产物 + 源码守卫锁 wiring）。

接 §4.46。用户点名"去广告我说的是金牌影视"。这次把它**从页面到流**测了个遍

## §4.55 「质感没变化」的真因是材质没对比 + BottomNavigationView 的间距改不了（v1.0.62，E32）

- **现象**：连续两版用户都反馈亮色 tab 栏「质感不好」。第一版只换配色、第二版加了
  选中胶囊 + 描边压深 + elevation 8dp，用户回复仍是「材质质感无变化」。
- **根因一（设计）**：亮色 Dock 一直是**白面板压在暖纸画布上**。白对暖白，
  明度差极小 —— 描边、圆角、阴影全在同一个色系里加参数，观感不可能变。
  材质层次的唯一来源是**前景与背景的明度对比**：改墨色 Dock（#1B2028）一次拉满。
  教训：用户说「质感没变化」时，先量前景/背景明度差，别继续调描边与阴影。
- **根因二（实现）**：BottomNavigationView 的 icon↔label 间距是库内固定值
  （BottomNavigationItemView 里约 4dp），**没有对外属性**；itemPaddingTop/Bottom
  只影响 item 内上下留白，改不了两者之间的距离。用户报「挤在一起」只能换手写 Dock。
  手写后图标 22dp / 间距 5dp / 栏高 64dp 全是自有 Token。
- **连带**：手写 Dock 丢了 menu 的 checked 状态机 ⇒ 选中态改由 View.setSelected
  驱动（会向下传播给子 ImageView/TextView），两个 selector 的状态键从
  state_checked 改成 state_selected；「刷底栏 + 切页」必须并成**一个入口**
  （selectTab），否则又会出现「内容回首页、底栏还亮着站源」。
- **守卫同批改**：runui50 原来锁 glass_stroke 与
  binding.bottomNav.selectedItemId = R.id.nav_home —— 都是**实现**。
  改成锁机制（「带 1px 描边」「经 selectTab 同步选中态」）。这是 PITFALLS §4.41
  「守卫锁机制不锁实现」的第二次实战，模式已稳定：**换代实现必红 ⇒ 先改判据再动代码**。
- **观察（未处理）**：rununiversal F5 活体段最近三版都偶发红。它是「守卫判定 ==
  实测逐字节相同」的等式，而站点首页含少量动态内容时，长度一致但链接集不同 ⇒
  守卫（宽判据）说副本、逐字节（严判据）说不是 ⇒ 红。属**夹具判据把两种粒度当成
  一回事**，非产品回归。修法建议：不可判定时 SKIP，而不是判 FAIL。

## §4.56 亮色主题里放深色 Dock = 主题反转（v1.0.63，E33）：上一版把「层次不足」修反了方向

- **现象**：v1.0.62 发版后用户装上，只有一句：「浅色模式 tab 栏是深色的，这明显不合理」。
  连"质感"两个字都没提 —— 说明问题已经不是**好看不好看**，而是**对错**。
- **根因**：§4.55 的「根因一」把两件事混成了一件：
  - 事实：v1.0.61 的白 Dock 观感"只是一块白" ✓
  - 错误归因：所以**要往暗里走**（墨岛 #1B2028）✗
  - 真正缺的东西：白面板当时**只有 fill + stroke 两层、且没有 elevation** —— 缺的是
    「投影」这件分层的第三件，不是缺明度反转。
  - **明度反转在亮色主题里就是主题反转**：它不是"更高级的对比"，是把界面拉去另一套
    主题的底色上。用户对此的判断是**对错层面**的，不是偏好层面的。
- **教训（可复用）**：修「对比不足」之前先问**该往哪个方向加对比** ——
  - 亮色主题：抬亮前景（白面板压暖纸）+ 描边 + 投影，靠"浮起来"分层
  - 暗色主题：提亮一档（黑场上再压暗 = 消失）+ 白发丝线
  - 「跨主题统一设计语言」= 统一**分层机制**，不等于统一**色值方向**。
    两条路方向相反，但表达的是同一件事：把 Dock 从画布里分出来。
  - 这条判据本身可写成断言（见下），说明它是**机制**而不是审美偏好。
- **连带（同一族静默坑）**：

  - 选中色**必须按自家 Dock 底色取，不能"统一"**：亮琥珀 #FFC46B 在白底只有

  - 面积色（选中胶囊 dock_pill）也一样：同样是琥珀 12%，在白底上淡到几乎看不出，
    提浓到 17%（#2BE8862C）才与白底分得开。
  - 未选中色同理不能沿用 text_hint：text_hint 只对"画布"负责，不对 Dock 底色负责。

## §4.57 沉浸式三连：假沉浸 / 漏刷选中态 / 透明化必须重算对比度（v1.0.64，E34）

用户同一轮给三条，逐条独立：
1. 「小白条没沉浸」
2. 「软件冷启动时，胶囊中首页理应为选中状态，但是目前无选中视觉效果」
3. 「tab 栏可以适当增加类似暗色模式下的透明效果」

### 现象一：假沉浸 —— 两条系统栏是"各自填一条同色"

- **表现**：屏幕底部永远杵着一条独立色带（暖灰 `bg_deep` 压在暖纸 `bg` 之下），
  颜色只差一点点，而且**不随内容滚动**。状态栏同理（`statusBarColor = @color/bg`）。
- **根因**：`decorFitsSystemWindows` 默认 true ⇒ 内容被系统限制在两条系统栏之间，
  系统栏区域由主题里的 `statusBarColor` / `navigationBarColor` 填色。
  于是"看起来没有突兀色差"被误当成"沉浸" —— 那是**同色**，不是沉浸。
- **修法**：三件事缺一不可（只做前两件 = 改了没用）：
  1. `WindowCompat.setDecorFitsSystemWindows(window, false)`
  2. 两条系统栏色置为 `Color.TRANSPARENT`
  3. **关掉系统的"对比度护航"**（API 29+ `isStatusBar/NavigationBarContrastEnforced = false`）——
     系统栏透明时系统会自作主张加一层半透明 scrim 兜底，不关掉的话 ①② 全白做
- **代价必须自己还**（最容易只做一半的地方）：
  - 顶部 inset → 根布局 `paddingTop`，否则首页首行顶进状态栏；
  - 底部 inset → **算进 Dock 的 `marginBottom`**，而**不是**给根布局加 paddingBottom。
    后者会让画布提前截止，又变回一条色带 —— 画布必须一路铺到屏幕底。
- ⚠️ 只在**本 Activity 的 window** 上做，**不写进 `themes.xml`**：主题是全局的，
  历史/收藏/投屏那几个 Activity 没有配套 inset 处理，改成透明后内容会直接钻进
  系统栏里，比现在更糟。主题里那两行保留给它们用（已在注释里写明这一层）。
- ⚠️ 状态栏图标明暗不在这里管：仍由 values-v23(-v27) / values-night-* 的
  `windowLightStatusBar` / `windowLightNavigationBar` 决定，两处都设会打架。

### 现象二：冷启动首页无选中视觉 —— 宣布了"唯一入口"却没让初始化走它

- **根因**：v1.0.62 手写 Dock 后，选中态由 `selectTab()` **唯一入口**负责，
  但 `onCreate` 收尾写的是 `showPage(PAGE_HOME)`（只切页、不刷选中态）——
  入口没被初始化走到，于是首页那格既没琥珀也没胶囊，点一下别的 tab 再点回来才"活"。
- **教训**：宣布"某入口是唯一入口"之后，**必须把初始化也改成走它**；
  否则"唯一"只是名义上的。这类 bug 不报错、不崩溃、不影响功能，
  只是少一个视觉状态 —— 典型"没有守卫就会静默存在"的形态。

### 现象三：底一变透明，文字色基准就跟着变（这是计算，不是审美）

- **背景**：暗色 Dock 一直是 `#F2`（95% 半透明），亮色却是 `#FFFFFFFF`（全不透明）。
- **修法**：亮色 `dock_fill` 降到 `#ED`（93%），`dock_fill_2` 再降到 `#E0`（88%）。
  两主题的 alpha **不能统一成一个数**：透明感来自"背后内容与本底的亮度差"，
  墨底压黑场 5% 就够，白底压暖纸要 7% 才等效。
- **关键（最容易错的一步）**：底一变透，对比基准就从"Dock 自身"变成"合成色"，
  而且**只测自家画布是不够的** —— Dock 是浮层，深色海报会整块滚到它正后方，
  那才是会砸锅的情况。按最坏情况（背后纯黑）重算：

  | 色 | 旧值·最坏情况 | 新值·最坏情况 | 新值·常态（压纯白） |
  |---|---|---|---|
  | 未选中 | `#64707F` 4.31:1 ✗ | `#5C6875` 4.86:1 ✓ | 5.69:1 |
  | 选中 | `#9E6709` 4.08:1 ✗ | `#8F5C08` 4.84:1 ✓ | 5.67:1 |

  - 顺带一个"试过才知道"的细节：先取 `#96610A`，最坏只有 4.47:1 —— **贴边不留余量**，
    弃用；压到 `#8F5C08` 才安全。
  - **不压深行不行**？不行。这正是"底一变透 ⇒ 文字必须跟着压深"的因果：
    只改 alpha 不动文字色，深色内容经过时文字会掉到 4.3:1 以下。
- 两条 alpha 的规矩（旧不变量延续）：`dock_fill_2` 的 alpha **不得大于** `dock_fill`
  （下沿不能比上沿厚）。但两主题**达标方式不同**：亮色靠降 alpha，
  暗色 alpha 持平、改用 RGB 压深（黑场上再降 alpha，浮岛边界会消失）。

### 方法论：vacuous 断言的两副面孔（同一处连踩两遍）

写"onCreate 必须走 selectTab"这条断言时，连写两版都**恒为真**：
1. 判据 `"selectTab(PAGE_HOME)" in onCreateBody` ⇒ 恒真。因为 onCreate 里本来就有
   `tabHome.setOnClickListener { selectTab(PAGE_HOME) }`。
2. 改成"看末尾 8 个非空代码行里有没有它" ⇒ **还是**恒真。窗口太宽，
   那行点击回调正好落在倒数第 8 行以内。
最终判据：只看函数**真正的收尾**（末 3 行、先剔掉纯花括号行）。

> 教训：写"某处调用了 X"这类断言，必须同时钉住**位置**。只判"文本存在"，
> 必被同文件里另一处相同调用蒙对。这与 §4.45「判机制生效只看决策、不看结果」
> 是同一件事的两面。**每加一条断言都要证伪一次** —— 本轮两版空断言靠证伪才发现。

### 守卫（runui50：A2 段续 7 条 + 新开 A3 段 9 条）

- A2 续：两主题 `dock_fill` 必须半透明（alpha < 1）；`dock_fill_2` 不得比 `dock_fill` 更实；
  亮色下段必须确实更透；**最坏情况（合成到纯黑）下选中/未选中仍过 AA 4.5:1**。
- A3 新：edge-to-edge 三条（decorFits / 双透明 / 关 contrast enforced）、
  inset 去向两条（顶部走 paddingTop、底部走 marginBottom 而非 paddingBottom）、
  Dock 底距与内容让位含系统栏两条、onCreate 收尾走 selectTab 两条。
- ⚠️ 全部用 `code()` 剥注释判 —— 这两件事在注释里被反复描述，不剥就是 §4.54 式弱校验。
- 证伪实测：亮色 `dock_fill_2` 改回全不透明 ⇒ 红 2 条；
  onCreate 收尾改回 `showPage(PAGE_HOME)` ⇒ 红 2 条。

## §4.58 网盘分享站落地：编译器给的假线索，与一条只有离线套件能抓的误判（v1.0.65，E31~E35）

本轮是「输入网址 → 识别 → 播放」主线的一次**加层**（快映4K / 玩偶4K 这类"详情页只有
网盘分享链接"的站）。方案见 `docs/网盘分享站适配方案.md`。四条新坑，两条是**工具的**，
两条是**判据的**。

### E31 所有 Adapter 都是 final ⇒ 新适配器**不能继承**，只能做装饰器

- **现象**：`class PanShareAdapter(site) : HtmlAdapter(site)` 报 **18 个错**，其中 17 个与
  继承毫无关系 —— 全是 `Type mismatch: inferred type is Unit but Document was expected`、
  `Unresolved reference: internal final var lastDetailDoc`、`receiver type mismatch`。
  看起来像"类型推断链从某一处塌了"，很容易顺着最后一行去改 `runCatching {}.getOrNull()`。
- **真因**：`HtmlAdapter` 是 **final**。错误清单里**唯一**一句真话是
  `e: PanShareAdapter.kt:55:43 This type is final, so it cannot be inherited from`
  —— 类没建起来，`this` 就成了错误类型，于是**所有成员访问**都变成"接收者类型不匹配"。
  后 17 条全是那条的连锁噪声。
- **通用机制（本项目的复用原语，别绕开）**：适配器家族一律
  `class X(site) : SiteAdapter(site)` 且各自 final；复用走**扩展函数**
  （`internal fun HtmlAdapter.hitDetail(...)` / `buildDetail(...)`）与**委托外壳**
  （`SeedRouter` / `FamilyRouter` 都是 `private val html` + 15 个契约成员全委托）。
  所以"给某一族加一个详情页行为"的正确姿势是**装饰器**：
  `class PanShareAdapter(site, private val html: HtmlAdapter = HtmlAdapter(site)) : SiteAdapter(site)`，
  只 `override detail()`，其余 14 个成员委托。
- ⚠️ **装饰器必须暴露 `val underlying: SiteAdapter get() = html`** —— 离线 harness 的
  `Chains.worksAs/hops` 靠它沿 `underlying` 剥到底（`instanceof HtmlAdapter` 那种判据在
  "多包一层"后本来就会假红，剥链是既定的解法）。漏了它，`runbs4` / `runlive2` 会红，
  而红的原因看起来像"工厂选错了适配器"。
- **判据**：编译错误清单里出现 `This type is final` 时，**先修它**，再看剩下几条还在不在。
  连锁噪声会自己消失；顺着噪声改代码会白改一整天。
- **源码守卫**：`PanLinkTest.java` E10 锁 `val underlying: SiteAdapter get() = html`；
  E12 锁"装饰器真的在委托"（`html.buildDetail(` + `html.detailUrlFor(id)`）。

### E32 ★ 网盘分享 id 的字符类必须排除 `.`（一条只有离线套件能抓出来的真误判）

- **现象**：`https://pan.baidu.com/s/1.html` 被解析成 `baidu:1.html`（长度 6 过闸）。
  后果不是"这条链接播不了"，而是**任何引用了百度页面的普通站点都可能被拖进网盘链路** ——
  `SiteAdapter.resolve()` 第 0 步是自门控入口，误判的代价是整个详情/播放走错路。
- **真因**：TVBox 原正则的 id 字符类是 `[^/\s?#"'<>&\\]+`（只排空白/引号/路径分隔符），
  `.` 是合法字符。而九个盘的分享 id 实际都只用字母数字（百度/迅雷另带 `_` `-`）。
- **修法**：八条规则的 id 字符类一律加 `.`（`[^/\s?#"'<>&\\.]+`）。
  ⚠️ **不要**顺手改 `139` 的**中间段**（`(?:…|[^/…]+/share/)`）—— 那是定位锚不是 id；
  也不要用"凡是 `]+)` 结尾就插一个点"的批量替换，否则会把 `[0-9A-Za-z]` 变成
  `[0-9A-Za-z.]`（`.html` 又好回来了，症状是"改完还是红"）。本轮就踩了这一步，靠复核计数抓回。
- **为什么只有离线套件能抓**：这个误判在真站上**不报错、不崩、也不影响那几部片子**，
  只在下一次遇到"内容里带 `pan.baidu.com/…html`"的站时才发作。
- **判据**：负例清单里放 `s/1.html` 与 `s/abc.html`（id 太短 ⇒ 挡掉），
  ⚠️ 但**不要**断言 `pan.quark.cn/s/{合法id}.html` 必须为 null —— 那会被当成合法分享
  （接口只认 id，`.html` 只是路径噪声），那是**对的**，锁成红的等于把守卫做错。

### E33 Kotlin 两条硬语法：同名 data class 与 object 不能共存 / 一个类只能有一个 companion

- 症状都是**几十个无关的 unresolved reference**，真正的原因只有一两行：
  - `data class PanLink` + `object PanLink`（想让 API 叫 `PanLink.parse`）⇒ 所有
    `PanLink.parse` 全部 unresolved，并连锁出 `Document was expected` 一类误报。
    修法：解析 API 搬进 `data class` 的 **companion object**（调用点形态不变）。
  - 一个类里同时写 `companion object` 和 `private companion object` ⇒
    `Only one companion object is allowed` + 常量 unresolved。修法：合并成一个。
- **判据**：错误数突然到几十而改动只有一两处新文件 ⇒ 先找"唯一那句描述真正问题的错"
  （final / Only one companion / 重名），别按错误数估计工作量。

### E34 离线 harness 上写 Java 断言的三个小坑

1. `runCatching { sp?.getLong(k, 0L) }.getOrDefault(0L)` 在 Kotlin 侧
   `Result<Long?>.getOrDefault(Long)` ⇒ **推断成 `Long?`**，赋值给 `Long` 直接编译错。
   正确写法 `… .getOrNull() ?: 0L`（`getOrDefault` 只对非空 T 顺手）。
2. Kotlin 属性名以 `is` 开头时，Java 侧 getter **不叫 `getIsVideo()` 而叫 `isVideo()`**
   （`getIsVideo` 会报 `cannot find symbol`，而 IDE 提示看起来很像"依赖没挂"）。
3. 本机 Git Bash 的 heredoc 里，**带反斜杠的 Python 字面量会被吞掉一半**
   （`r'[^/\s…\\]+)'` 到达脚本时只剩一个 `\`，表现是 `s.count(old) == 0` —— 字符串明明在）。
   凡是要匹配含反斜杠的源码，改用**不含反斜杠的锚点**做替换（例：把 `]+)"""` 换成 `.]+)"""`），
   并在替换后**打印计数复核**（见 `win-gitbash-build-env-pitfalls`）。

### E35 ⚠️ 未修：`rununiversal` 的 F5 是**探针太严**，不是站点漂移（存量红）

- **现象**：`rununiversal` 持续 `BAD PASS=40 FAIL=1`，唯一失败是
  `F5 守卫与实测一致 … 守卫=true 实测逐字节相同=false`。
  `_runall.log` / `_runall2.log`（本轮改动**之前**）已经是同一条红 ⇒ **存量红，与 v1.0.65 无关**
  （`SoftMiss.kt` / `Universal.java` 本轮未改）。
- **真因**：F5 的 oracle 只实现了 tier ①（`len` 一致 + `linkHash` 一致），
  而 `SoftMiss.whyCopyOf` **刻意有两档**：②「标题相同 + 唯一链接数相同 + 长度差 <1%」
  专门兜"随机广告位 / 时间戳"。该站现在的软 404 落在 tier ② ⇒ 守卫判"是副本"（正确），
  F5 却按 tier ① 判"不是"⇒ 断言红。**是 oracle 与实现的两档定义不一致，不是守卫错**。
- **处置**：未动。要么把 F5 的 oracle 升级成两档（**注意别直接调 `isCopyOf`，那会变成循环论证**），
  要么把 F5 降级成 `note`。它属于 `runall.py` 文件头讲的"活体断言分类"问题，
  改动会动到 SoftMiss 的语义，留待确认。

### 二、★ E36：`+` 没编码 ⇒ 间歇性"非法token"（差点写成假结论）

**现象**：`dbc851025443` 稳定报 `400 code:14001 Bad Parameter: [非法token]`
（连打 3 次、3/3，**不是抖动**），而同一时刻另两条全绿。
第一反应是"这条分享失效了"或"玩偶站一半线路是坏的"。

**对照实验**（构造 `aaaaaaaaaaaa` 这种必然不存在的 id）才看清：不存在的分享报的是
**41006 分享不存在**，而这条在 token 阶段是 **200 且 title 正常**
（`下一顺位是她 [2025]`）⇒ **14001 ≠ 分享失效**。

**真因**：它的 stoken 长这样 —— `+JPpdVNi4j…`，**以 `+` 开头**；另两条以字母开头
（`HznW…` / `PmC2…`）。脚本手拼 URL 时没编码，`+` 在 query string 里被服务端解释成
**空格** ⇒ token 变成非法。补一层 `quote(st, safe='')` 后**三条全部 200**。

**一眼认出的判据**：同一接口上**一部分请求成功、另一部分报同一个错误码**，
且失败那批的输入里带非字母数字字符（`+` / `/` / `=`）⇒ **先怀疑自己漏了 URL 编码**，
别归因站点、别归因"接口改版"。

**对代码的影响**：App 里 `PanCloudDrive.u()`（`URLEncoder.encode`）一直在做这件事，
**它是必需的** —— 已在该函数上写 KDoc 明说"不要删"，并附这条实测依据。
这个坑危险在于**间歇发作**：同一部剧今天能展开、明天报"非法token"，
只取决于当次 stoken 里恰好有没有 `+`。属于 MEMORY 里"全绿 ≠ 没问题"那一类。

### 三、顺带证伪的两条（省下一次探索）

1. **UC 那张桌子不是"同一份分享换个域名"**：拿夸克分享 id 去打 `pc-api.uc.cn`，
   token 阶段照样 200 给 stoken，但 detail 立刻 `400 code:14001 [非法token]`。
   ⇒ 两品牌后端同构、**分享命名空间不互通**。所以 `PanType` 必须按域名分桌
   （`pan.quark.cn` → `.quark()`、`drive.uc.cn` → `.uc()`），不能"哪个盘子都试一遍"。
   （注：这条最初被我当成 14001 的解释，直到第二个对照实验才分清 ——
   两个不同的原因**恰好报同一个 code**，这正是它能骗过第一轮的原因。）

## §4.60 取流入口不是 `file/download`：一条被文案骗到的死路，与"清理"的三种静默（v1.0.65，E38~E39）

这一节是 §4.59 的续：拿到**真正**的登录态 Cookie 之后，第一次把 ⑤ 完整链路跑通，
结果**推翻了我 P0 的取流设计**。三件事全是实测，别再凭"接口名字看起来该干什么"推。

### 一、E38：`POST /file/download` 对普通账号已经不给直链了

原设计（方案文档 §5）：`save` 转存 → `task` 轮询 → `file/download` 取直链。
带真实登录凭据打过去，**对分享里的每个文件**都是：

```
400 code:23018  message: download file size limit[<fid>]
```

**`size limit` 这个名字会骗人。** 同一账号同一分享里，742MB 的被拒、
615MB 的"最小文件"**也被拒** ⇒ 不是体积问题。六种组合逐一试过，全一样：
换 host（`drive-pc` / `drive-m`）、换 UA（桌面 Chrome / 夸克 App）、换 Referer、
加 `?pf=1&support_https=1`、加 `group_id`。

**正确的入口是 `POST /file/v2/play`**：

```json
请求体 {"fid": "<文件fid>", "resolution": "normal"}
⇒ 200 code=0，data.default_resolution = "super"
  data.video_list[] = [ {resolution:"super", right:"svip", trans_status:"success",
                         accessable:true, video_info:{url:"…/media.m3u8", width:1440, bitrate:…}},
                        {resolution:"high", …}, {resolution:"low", right:"normal", …} ]
```

**取档判据：用服务器自报的 `default_resolution`**，别自己挑。
各档还带 `right`/`member_right`/`trans_status`/`accessable`/`width`/`bitrate`/`size`
—— 将来要做"会员过期就降档"，判据就在这几个字段里，不用猜。

退路：`GET /file/play?fid=…&resolution=raw|low`（实测两档都能出 URL，
`raw` 与 v2 的 `super` 指向同一个 m3u8 路径）。`v2/play` 拿不到 URL 时才走。

**为什么这反而是好事**：它返回的是转码后的 HLS 播放列表，**文件多大都不影响**
（2.9GB 的片子 = 1038 个分片，播放器按需拉），不必先把整个文件下下来 ——
也就没有"下载超时/占满带宽"这类问题。

### 二、m3u8 / ts 的校验强度（这张表决定 P2 本地代理**不必做**）

同一份 `media.m3u8` 与首个 `.ts`，每次只改一个变量：

| 请求头 | m3u8 | ts |
|---|---|---|
| UA + Referer + Cookie | **200** `#EXTM3U` | 200 |
| **仅 Cookie** | **200** | 200 |
| 去掉 Cookie（对照） | **412** | 412 |
| 仅 UA | **412** | — |
| 仅 Referer | **412** | — |
| 什么都不带（裸） | **412** | — |
| 仅 Cookie + `Range: bytes=0-1023` | — | **206** |

最小 Cookie 键集（这决定播放器要注入多少）：

| Cookie | 结果 |
|---|---|
| `__puus` 单独（255 字符） | **200** |
| `__pus` 单独（126 字符） | 412 |
| `__uid` 单独（30 字符） | 412 |
| `__pus+__puus` / 三者 / 全量 1281 字符 | 200 |

播放列表本体：`#EXT-X-ENDLIST` 有、`#EXT-X-PLAYLIST-TYPE:VOD` 有、
`#EXT-X-KEY` **0 处**（不加密）。

⇒ **结论**：只认 Cookie，**不认 UA/Referer**；ts 支持 Range（206）⇒ ExoPlayer 能直连拉分片并 seek；
不加密 ⇒ 不需要解密层。⇒ **P2「本地代理」不必做**，只要 `MediaSource.Direct` 的
headers 里带上 Cookie（App 里就是 `MEDIA_COOKIE_KEYS` 白名单）。

### 三、E39：`file/delete` 的三种静默，以及"立刻删"是**必败路径**（一次被自己写错的结论）

清理转存产物这件事，**从头到尾都在静默失败**，而且我第一次的结论也是错的。

#### 3.1 先纠一条我自己写错的结论

首轮看到"同样的 body、4 次连续 `500 code:15000 inner error`"，我判成**瞬时抖动**，
处置是"用 `Http.postJsonOrNull` 的 5xx 退避重试覆盖它"。这个判断**是错的** ——
后来做了对照，四行的结果摆在一起才看清：

| 序列（同一份凭据、同一个 body） | delete 结果 |
|---|---|
| save → **不调 play** → 立刻 delete | **200 code=0** ✅ |
| save → `v2/play` → **立刻** delete | **500 code:15000** ❌（连试 4 次全败） |
| save → `v2/play`（**只调 play、没拉流**）→ 等 45 秒 → delete | **200 code=0** ✅ |
| save → `v2/play` + **真拉 m3u8 与 ts** → 等 45 秒 → delete | **500 code:15000** ❌ |
| 同上 → 等 **120 秒** → delete | **500 code:15000** ❌ |
| 同上 → 约 **140 秒** → delete | **200 code=0** ✅ |
| 放置 2~3 分钟的旧文件 → delete | **200 code=0** ✅ |

⇒ 真因是 **`v2/play` 打开了播放会话，该文件被锁住，之后自己松开** ——
而且**拉过流（m3u8/ts）会锁得更久**：只调 `play` 时 45 秒就够；拉过流时
**45 秒、120 秒都实测失败**，到 ~140 秒才成。第一行是关键对照：
**不播就能立刻删** ⇒ 排除"刚转存完数据没落盘"。

> ⚠️ **锁定窗口没有可靠值**（不是"恰好 2 分钟"）：同一量级上 120s 失败、140s 成功，
> 另一轮 ~120s 又成功 —— 服务端大概是**惰性回收会话**，有抖动。
> ⇒ **别把某个秒数当判据**（更别写成 `delay(120_000)`）。这也正是本项目
> 处置用**排队重试**而不是定时器的原因：对任何窗口都成立。

**所以"拿到 URL 就立刻删"是必败路径**：硬删既留残留、又白等一轮重试（≈2.4s）。
**"连续失败 4 次"被误当成"抖动"**，正是因为没有做"换个变量"的对照 ——
这与 E36（漏编码）、E37（Cookie 长相）、E38（`size limit` 文案）是**同一个错误**：
**看到报错就去猜原因，而不是先造对照组。**

#### 3.2 三个叠加的静默性质

1. **参数名只认 `filelist`**。用 `{"fids":[…],"pdir_fid":"0"}` 恒
   `400 code:14001 [current_dir_fid,filelist 不能同时为空]` —— 报错**不点名**，
   只说"不能同时为空"，很容易读成"少了 pdir_fid"。实测三种形状正好把答案夹出来：
   - `{"fids":[…],"pdir_fid":"0"}` → `14001 [current_dir_fid,filelist 不能同时为空]`
     （⇒ 参数名被忽略，它只认 `filelist`）
   - `{"filelist":[…],"current_dir_fid":"0"}` → `14001 […不能同时存在值]`
     （⇒ 两者只能给一个）
   - `{"action_type":2,"filelist":[…],"exclude_fids":[]}` → **200 code=0** ✅
2. **它是异步任务**。200 时给 `{"task_id":"…","finish":false}`，文件**随后**才消失；
   成功之后再删同一个 fid 会得到 `400 code:23004 [文件已经删除]` —— **HTTP 400**，
   所以"看不到 body 的调用方"只能返回 `false`。**这不代表失败**（盘里是干净的）。
3. **它会被播放会话锁住**（见 3.1）。

#### 3.3 处置（写进 App）

- `delete()` 用 **`Http.postJsonOnceRaw`**（v1.0.65 新增：单发、不重试、不抛，
  返回 `(HTTP 状态码, 响应体)`，仍记 `NetLog`）。原来的 `postJsonOrNull` 会走
  5xx 退避重试 —— 清理接在**用户等待路径**上，让它白自旋 2.4 秒去撞一个
  **必定失败**的请求，纯亏。
- **按状态码三分派**（这是把"必败"和"抖动"分开之后的自然结论）：
  | 状态码 | 含义 | 处置 |
  |---|---|---|
  | `200` | 成了（异步任务） | 出队 |
  | `4xx` | `23004 文件已经删除`=盘里本来就干净；`14001`=参数错 | **出队，别再试** |
  | `5xx` / 网络失败 | 播放会话还锁着 | 留在队列，下次再试 |
  > 用"HTTP 4xx 一律出队"代替"去解析 `23004` 的正文"：`oncePostJson` 对非 2xx
  > **抛异常、正文拿不到**，而 `23004` 与 `14001` 的处置**恰好相同**（都不该重试）
  > ⇒ 只看状态码就够，不必为此再加一层能读 4xx 正文的 API。
- **不立刻删，改成"记账 + 下次顺手清"**：
  - 取流成功后把 fid 记进 `pendingDelete`（内存队列，`fid → 首次记账时刻`；fid 不是密文，但也不必落盘）；
  - `stream()` / `list()` / `verify()` 的**入口**先 `sweepPending(ck)`（一次最多 3 个）——
    那时它们是"上次那集"，已经凉了，删得掉；
  - 取流**失败**时（没有播放会话）反而可以立刻删 —— 这是 3.1 第一行给的许可；
  - 条目超过 `PENDING_TTL_MS`（6 小时）放弃、队列上限 32（丢最旧）——
    两道闸门只为"别让真删不掉的东西无限重试"，正常情况队列里只有 1 个；
  - 效果：盘里**最多同时积压 1 个**转存产物，并在下次网盘操作时被清掉。
- 清理失败**不许写 `err`**：流已经拿到了，把它报成"播放失败"是错的。
- 顺手确认了一条好性质：**删掉转存产物后，已签发的 m3u8 与 ts 仍 200**
  ⇒ 清理可以随时做，不必等播完。

**残留已知的取舍**（写进 KDoc，别当没这回事）：队列只在内存里 ⇒ 进程被杀时丢失，
"最后一次播放留下的那 1 个"就清不掉了；且"清不掉"这件事**本身是静默的**
（用户不会看到任何提示）。要彻底根治只有两条路：① 把待清理 fid 落进 `DriveStore`
（多一层存储耦合，换"少 1 个文件"），② 换一个不受播放会话影响的删除姿势（未找到）。
**当前选的是不根治 + 写清楚**。

#### 3.4 副产品：E36 又一次被自己踩到

写这次对照实验的脚本时，我把 stoken **未编码**塞进 query，立刻收到
`400 code:14001 Bad parameter: [非法token]` —— 原因正是 E36 那条（这次的 stoken 是
`S3yuqbr+txLyhZKQh/3t…`，含 `+` 与 `/`）。**同一个坑在同一个会话里被踩了第二次**。
⇒ 该判据值得升级成"凡把服务端给的 token 塞进 query，先看一眼字符类"的条件反射；
本项目里的落点是 `PanCloudDrive.u()` 与 spike 里的 `eq()`（两处都带 KDoc 警告"不能省"）。

### 四、纪律（这轮的三条可复用判据）

1. **报错文案会骗人**：`size limit` 名字像"文件太大"，但对照组（更小的文件）同样被拒。
   ⇒ 凡按错误文案归因，**必须带对照组**（E36 的 `14001`、E37 的 Cookie、E38 的 `23018` 是同一课）。
2. **"取流入口"要靠端点矩阵实测，不靠命名直觉**：
   `share/sharepage/{download,file/download,video/play,play}` 四个"看起来该有"的全 **404**；
   `/file/v2/play` 回 **405 GET not supported**（⇒ POST 可用）——
   405 这个信号本身就是"端点存在、只是方法不对"，别当 404 处理。
3. **手抄长凭据进命令行 = 间歇性"会话失效"**：把 1281 字符的 Cookie 手打进 shell，
   一个字符之差（`…C8wr9kz…` 打成 `…C8wr7kz…`）表现为"上一轮还好、这一轮突然 31001"。
   ⇒ 凭据一律**落文件 + 以长度自检**（`wc -c` / `len(ck)`），别手抄。这与 E29 的
   "工具假成功"是同一类：**别信手抄/返回值，要有一个不依赖人的校验**。

### 五、未做（勿当已完成）

- **真机 spike**：`adb devices` 为空（adb 在 `D:\Android\Sdk\platform-tools\adb.exe`），
  "ExoPlayer 播起来"这半**没做**。PC 侧已验到"m3u8 能被带上 Cookie 拉下来"，
  但 **ExoPlayer + HLS + 自定义 header 的实际播放**仍未验证。
- **stoken 提前失效没有自愈**：缓存 20 分钟，服务端若提前作废会连续失败到 TTL 过期。
  按"卡住自愈 = 重新解析换令牌"的惯例应加"清缓存 + 重试一次"，属功能改动，**未加**。

## 4.61 网盘转码流的"播放卡顿"：HLS 分片**并发预取**（v1.0.65）

> 需求原话：**「你参考下潇洒 tvbox 本地包的做法，他的是成功的，且注意多线并发加速
> 也可以参考下，否则容易卡顿」**。这一节记的是"怎么在**不引入本地代理**的前提下
> 落地多线并发"，以及这条路上踩到的 4 个坑。

### 一、先定性：卡顿的根因不是"网络不好"

网盘给的 `media.m3u8` 是**转码流**，分片在 CDN 上、**单连接限速**；
而 ExoPlayer 拉 HLS 是**一个 Loader 顺序拉**（点播清单也一样）：分片 A 下完才去下 B。
于是 **有效吞吐 = 单连接的吞吐**，一旦低于码率就反复把缓冲耗干。

症状是**「刚起播很顺，几秒后开始转圈，等一会儿又顺」**，而且：
- 网络诊断全绿（不是超时、不是 4xx）；
- 播放记录里**一条错误都没有**（它只是慢）；
- 换个低码率档就正常（⇒ 佐证是吞吐而不是连通性）。

⇒ **不要**照着这个症状去改请求头/重试/超时（那是 E27/E36 那类问题的解）。
这一步的判据是：**同样能播、只是"供不上"**。

### 二、为什么不做 TVBox 那种本地代理

潇洒 TVBox 本地包的做法是"起本地 HTTP 服务 + `quark_thread_limit:32` 并发下载"。
我们**不做代理**，理由是实测出来的（§4.60 那张表）：

| 本地代理通常要解决的问题 | 我们的实测结论 |
|---|---|
| 补 `Referer` / `UA` | 只认 **Cookie**（裸链/仅 UA/仅 Referer 一律 412）⇒ 播放器自己带头即可 |
| 绕 `Range` 支持差 | ts 带 `Range` 回 **206** ⇒ 播放器原生 seek 没问题 |
| 解密分片 | `#EXT-X-KEY=0`，不加密 |
| 改 `m3u8` 正文（重写分片地址） | **不需要** —— 分片地址本来就能直连 |

⇒ 代理**唯一的**剩余价值就是"并发"，而并发完全可以在
`androidx.media3.datasource.DataSource` 这一层做掉：清单到手时把"接下来几片"提前拉进内存，
播放器来读时命中、零等待。省掉的是：一个 HTTP 服务、正文重写、端口/生命周期，
以及"代理挂了整集全黑"这个新故障面。

### 三、设计（`player/HlsPrefetch.kt`）

- **只对点播清单生效**：无 `#EXT-X-ENDLIST`（直播）或含 `#EXT-X-STREAM-INF`（master）直接放弃；
  少于 `MIN_SEGMENTS`（6）片也放弃 —— 预热反而抢播放器的带宽。
- **窗口 8 片**（约 20~50 秒提前量），**并发 4**，**缓存上限 48MB**（LRU）。
- **单片超过上限就整片不缓存** —— 否则会把已有缓存全冲光，命中率反而崩。
- **连续 3 片拿不到就停**：这时正确动作是**把带宽让回播放器**（它自己有退避重试），
  而不是继续并发抢。
- **换源作废**：`generation` 自增，旧清单的在飞任务回来时丢弃结果。
- **拉片动作是注入的**（`fetch: (String) -> ByteArray?`）⇒ 离线 harness 能真跑每一条约束。
- 观测点：`PlayLog.record("⚡ 分片并发预取：本清单 N 片…") / "⏸ 预取已停…"` ——
  **判定机制有没有生效只看这几行**，不看"代码里有那几行字"。

### 四、这条路上的 4 个坑（每个都"不报错"）

#### 4.1 淘汰后重拉 = 无限拉取（E41，被离线 harness 抓到）

窗口按**播放位置**算、缓存按 **LRU 淘汰** ⇒ 被淘汰的片**立刻落回窗口**、重新拉、再淘汰。
harness 记到 **5784 片**（本该 8 片）。
修法：`queuedUpTo`（排过队的不再排），窗口只单向前进。
⇒ 教训：**"内存换流畅"的代价里不能包含死循环**；这类约束必须**真跑**（假 fetch + 计数），
只读源码是看不出来的。

#### 4.2 `maxRequestsPerHost = 5`（E40 ②）：预取把播放请求挤进队列

OkHttp 的 `Dispatcher` 默认**每 host 最多 5 个在飞**。预取 4 条 + 播放器 1~2 条 ⇒ 顶到上限，
播放器自己的分片请求要**排队等预取腾位置**。症状与"单连接限速"一模一样，但成因相反。
修法：给 `Http.mediaClient` 一个**独立 Dispatcher** 且 `maxRequestsPerHost = 8`
（4 条预取 + 4 条留给播放器自身）。守卫 `G4` 钉住。

#### 4.3 顺序坑：缓存判断必须在 `upstream.open()` **之前**

写反了不报错、也不影响正确性 —— 只是"先发起请求、再从缓存读"，
预取省下的时间全白搭、还平白多占一条连接。守卫 `G2` 是**顺序守卫**。

#### 4.4 游标初值必须是 `-1`

`schedule()` 从 `cursor + 1` 开始排；游标用 `0` 当起点会**跳过第 0 片** ——
那恰恰是起播最要紧的一片（"预热了但起播那一下照样等"）。harness `P1b` 钉住。

### 五、判据（`runhlsfetch`，35 条）

**真跑逻辑**（不是读源码猜）：并发峰值、预热含第 0 片、直播/master/短清单不预取、
命中/未命中、字节上限、单片超限不缓存、连败即停且停后不再发请求、滑动窗口推进、
不重复拉、换源作废、`stats()` 观测点、与 `HlsPlaylistFixer` 的协同（广告剔除/绝对化/补 ENDLIST）。
外加 6 条**接线守卫** `G0~G6`（含 `G0b` 剥注释自测）—— 防"预取器全绿但装配被摘掉＝完全没效果"。

> `G5` 曾经被判红：`HlsPrefetch.kt` 的 KDoc 里**故意**写着"不做 127.0.0.1 转发"这个反例。
> 与 `PanLinkTest` E5/E13a 同一个坑 ⇒ **凡"代码里不许出现 X"的断言，先剥注释**，
> 并补一条"KDoc 里确实保留着反例"的自测（否则断言之于**恒真**）。

### 六、未做

- **真机验证**：`adb devices` 仍为空 ⇒ "预取在真机上确实把卡顿治好了"没验（离线只能证决策与计数正确）。
- **实测并发拐点**：4 是参考值（潇洒给的是 32，那是代理整集的场景），
  没有真机测过"2/4/6/8 哪一档对这类 CDN 最优"。
- 未做"**多线路**并发择优"（用户话里的"多线"若指多线路而非多线程）：当前只对**同一路**的分片并发。

## §4.62 发版链路上两个"看起来不可能是这里"的坑（v1.0.65，E42/E43）

v1.0.65 是**第一次把中文文件名提交进仓库**，也是**第一次按双编码验包**。
两个坑都落在"过程全绿、结果不对"这一层 —— 同属 §4.34 那个母题。

### 一、E42：`TREE MISMATCH` 不是网络问题，是**路径被 git 转义了**

现象干净得不正常：

```
已上传 47/47 (8s)
blob 上传完成：成功 47/47
FATAL: TREE MISMATCH @ ece0e016df server=f6a8e1f7... local=76973c9b...
```

blob 一个不少、一次重试都没有，却在组装 tree 时对不上。

**诊断手法**（值得复用）：不要猜，把两侧**逐条目**比出来 ——
本地 `git -c core.quotepath=false ls-tree -r <commit>`，服务器
`GET /git/trees/<server_sha>?recursive=1`，按 path 建字典求对称差。结果：

```
DIFF "docs/\347\234\237\346\236\234\351\211\264_..."   local=None  server=('100644','fcb74237...')
DIFF docs/真果鉴_视频源解析.md                        local=('100644','fcb74237...') server=None
差异条目总数 = 4
```

**4 处差异全是两条中文路径**，而 blob sha 与 mode **两侧完全一致** ⇒ 内容没问题，
问题在**路径字符串本身**。

根因：`git ls-tree` 默认 `core.quotepath=true`，把非 ASCII 路径**转义**成
`"docs/\347\234\237..."`（带引号、带反斜杠的八进制）。推送脚本把这个字符串原样发给
GitHub 当路径 ⇒ 服务器上建出一棵**文件名乱码**的 tree ⇒ sha 必然不匹配。

**为什么现在才炸**：这是仓库**首次**提交非 ASCII 路径。这条链路上跑过几十次发版、
一次没撞过 —— 不是因为它安全，而是因为**从没被触发**。

修法两条（缺一不可）：

1. `git -c core.quotepath=false ls-tree -r <commit>`；
2. **加闸**：path 以 `"` 开头就 `die`。因为 `quotepath=false` **只关掉非 ASCII 的转义**，
   含空格/引号/控制字符的路径**仍然**会被引号包裹 —— 那种情况脚本处理不了，
   宁可当场红，也不要静默建出一棵错的 tree。

> 也暴露了这类脚本的坏处：它**只在最后一步**才发现不对，前面每一步都是绿的。
> 所以修完之后要再验一遍 **`commit sha` 与本地逐字节相同**（`commit ok ece0e016df`）——
> 那才是"对象图完全一致"的判据，`PUSH DONE` 不是。

### 二、E43：验包时**对照项自己先失效**了

验包脚本第一版：

```
对照·必然存在(包名)   arsc  NOT FOUND  <<< 不符
新·扫码自动保存提示    arsc  FOUND      OK
```

对照项红了，中文新文案全绿。**这时最诱人的错误结论是"包有问题"**（对照项本该"必然存在"，
它找不到 ⇒ 该怀疑包）。实际是**搜法**的问题：

```
MANIFEST videoshell 出现 0 次          ← UTF-8
MANIFEST UTF-16 里 videoshell: 18      ← UTF-16LE
```

`AndroidManifest.xml` 的字符串池是 **UTF-16LE**。于是：

- 只搜 UTF-8 ⇒ 对照项**必然**假 NOT FOUND（于是"对照"变成噪音）；
- 更要命的是**反方向**：旧文案若也在 UTF-16 池里，"旧文案 NOT FOUND"会**假绿** ——
  而 §4.38 要防的恰恰是"新旧两代同名同版本号包"，正是靠这条断言吃饭。

修法：**CASES 里每一项都双编码**（UTF-8 + UTF-16LE），不只版本号。判据纪律升级一句：

> **对照项必须能证明自己搜得着。** 一个永远不会红的对照，等于没有对照。

修完（并在 dex 侧也补一个 `com/videoshell` 对照）：

```
版本串 1.0.65 FOUND            版本串 1.0.64 NOT FOUND
对照·必然存在(包名)   arsc FOUND  OK     对照·必然存在(dex类名) dex FOUND  OK
对照·必然不存在       arsc NOT FOUND  OK
新·扫码自动保存提示   arsc FOUND  OK     旧·我已完成登录(应无)  arsc NOT FOUND  OK
新·预取观测文案       dex  FOUND  OK     旧·file/download(应无) dex  NOT FOUND  OK
本包不符项 = 0
```

### 三、纪律

- **"首次"是坑的放大器**：非 ASCII 路径、双编码、中文文件名 —— 每一样都是"一直都没事"
  直到第一次。凡"从没失败过"的路径，都要问一句：它是真的稳，还是**从没被触发**？
- 长链路（上传 → 组装 tree → 提交 → 打 ref）里，**每一步绿灯 ≠ 对象正确**；
  判据要落到**最终对象**上（commit sha 逐字节相同 / 树逐条目相同）。
- 验包工具本身也要**带对照、双编码**才算数（E43）。

## §4.63 「asset 丢了」是一次假红：观测点自己不可靠（v1.0.65，E44）

发版核 asset（§4.37 第三步）时：

```
$ gh api repos/.../releases/tags/v1.0.65 --jq '.assets|length'
0
$ gh release view v1.0.65 --json assets --jq '.assets|length'
0          # 而 v1.0.60~v1.0.64 都是 2
```

CI 日志却是：

```
08:50:31.151 ✅ Uploaded version.json
08:50:31.202 ✅ Uploaded app-release.apk
08:50:31.752 🎉 Release ready at .../releases/tag/v1.0.65
```

**两侧直接矛盾。** 我选了"CI 日志在骗人"，开始准备手动补传 —— 这个方向差点造成真实损坏：

- `gh release upload --clobber` 会**先删同名 asset 再传**；
- 我手上只有**本地包**（3,219,575 B），而 release 上是**CI 包**（3,219,578 B，§4.38 记过这类 3 字节差）；
- `version.json` 里的 `sha256` / `size` 是**CI 包**的 ⇒ 覆盖后 **App 内自更新会校验失败**，
  而现象是"提示更新、下载完装不上"，离根因十万八千里。

真正拦下它的是：

```
HTTP 422: Validation Failed (.../releases/394464710/assets?...name=version.json)
ReleaseAsset.name already exists
```

**asset 一直都在。** 换端点立刻证实：

```
$ gh api repos/.../releases/394464710/assets --jq '.[] | "\(.name) \(.size)"'
app-release.apk  3219578
version.json     428

$ gh api repos/.../releases/latest --jq '"\(.tag_name) assets=\(.assets|length)"'
v1.0.65 assets=2
```

### 根因

`/releases/tags/{tag}` 的 `assets` 字段对**刚创建的 release** 返回**空数组**（一致性延迟）：
列表端点里 v1.0.65 是 `assets=0`、v1.0.64 是 2 —— **同一个字段、两个 release 表现不同**，
说明问题在读数那一刻，不在 release 本身。

另有一个**我自己的用法错误**被当成了旁证：`GET /releases/tags/v1.0.65/assets` 返回 404 ——
那个端点**只认 release id**，不认 tag。我把这个 404 读成了"assets 确实没有"。

### 纪律

- **两个观测点打架时，先怀疑观测点**（§4.45「只看决策不看结果」的姊妹条）。
  尤其当一方是**间接字段**（`assets` 数组长度）、另一方是**动作的回执**（上传接口返回的 asset 对象）时，
  **回执更接近事实**。正确顺序是：**先找一个能直接证伪的端点**（这里 `/releases/{id}/assets`），
  再决定要不要"修"。
- **"会删东西的修复"必须先证伪**：`--clobber` / `--force` / 覆盖式上传这类动作，
  在证据链有矛盾时**一律先停**。上文那个 422 只是运气好。
- **核 asset 的正确姿势**：`/releases/{id}/assets`、`/releases/latest`，
  或**直接 HEAD 用户会点的那条 URL**（`/releases/download/<tag>/app-release.apk`）。
  后者最贴近"用户拿得到"，已加进 workflow（`Verify user-facing download URL`，带 5 次重试等 CDN 传播）。
- **拿不到包本身时的替代核对**：CI 日志里 `Generate version.json` 打印了
  `sha256=7a0cbeb9… size=3219578`，与 release 上 asset 的 size **逐字节一致** ⇒
  既证明 asset 是 CI 那份，也证明 `version.json` 与它**自洽**（自更新可用）。
  （本机直连 `github.com` 的下载 CDN 会被 reset，所以"下载下来扫一遍"这条路走不通 —— 见 §4.62 同源环境限制。）

## §4.64 扫码登录"没多久就过期"：手写的 Cookie 被 CookieJar 覆盖（v1.0.66）

### 一、症状（用户上报，真机）

扫码登录 → 界面提示"登录成功" → **过一会儿**（用户那次约 15 分钟）再打开「网盘账号」：

```
夸克网盘    登录已过期 · 09-23 17:30 更新      退出登录 / 重新登录
toast：夸克网盘 凭据未能通过校验，请重新登录
```

关键在"**登录当次是通过的**"（`DriveLoginActivity.captureAndFinish` 只有在 `verify()` 返回 `Valid` 时才
`finish()`，否则会 toast `drive_login_bad` 并留在页面上）。所以不是"没登上"，而是**登上之后凭据被弄坏了**。

### 二、机理：OkHttp 无条件用 CookieJar 覆盖手写 `Cookie` 头

网盘登录态是 `DriveStore` 里的一整份 cookie（`__pus` / `__puus` / `__uid` …），
由 `PanCloudDrive` 以**显式 `Cookie` 头**挂上去 —— 这是刻意的：它属于"与站点解耦的另一套凭据"，
不进 `Http` 里那个服务于站点解析的 CookieJar。

而 OkHttp 的 `BridgeInterceptor` 是**无条件**覆盖：

```java
List<Cookie> cookies = cookieJar.loadForRequest(userRequest.url());
if (!cookies.isEmpty()) requestBuilder.header("Cookie", cookieHeader(cookies));
```

于是时间线是：

| 时刻 | jar 状态 | 服务器实际收到的 Cookie | 结果 |
|---|---|---|---|
| 第 1 次请求（登录后的 `verify()`） | 空 | 我们手写的整份（`__puus` 在内） | ✅ 通过 |
| 该次响应 | 被服务端 `Set-Cookie` 填上 | — | （此时已埋雷） |
| 第 2 次请求起（每次进账号页、每次列目录） | 非空 | **只有 jar 里那点**（`srvmark` 之类） | ❌ `31001 require login` ⇒ `markExpired` |

### 三、判定：本机起 HTTP 服务真跑，不靠读文档

`tools/verify/OkHttpCookieJarTest.java`（`runokcookie` 套件，**不联网**）把机理钉死：

```
A 第 1 次服务器收到 : __pus=aaa; __puus=bbb; __uid=ccc
A 第 2 次服务器收到 : srvmark=1        ← 整份登录态被替换
B 修后三次          : 每次都收到 __pus=aaa; __puus=bbb; __uid=ccc
C 摘掉 jar（对照）  : 每次都收到手写值（证明观察点有效）
D 不带显式 Cookie   : 收到 srvmark=1（jar 照常工作，站点解析不受影响）
E 把 restore 挂错位 : 第 2 次仍被覆盖（**静默失效**，编译无警告）
```

**E 组是最值钱的一条**：`restore` 挂 `addInterceptor`（application 位）与挂 `addNetworkInterceptor`
（network 位）**代码看起来一样、编译都过**，但前者跑在 `BridgeInterceptor` 之前 ⇒ 完全无效。
所以 PanLinkTest 的 `E18b` 守卫专门钉"必须是 network 位"，且**禁止** application 位那种写法出现。

### 四、排除掉的假设（都认真查过）

| 假设 | 为什么不是它 |
|---|---|
| cookie 被服务端提前作废（轮换 `__puus`） | PC 侧 spike 用**同一份** cookie 连打十几个接口（token→detail→save→task→play→delete）全部成功（§4.60）⇒ 短时内旧值仍有效。而且"登录当次通过"正好对应"jar 还空着" |
| 存盘坏了（加密/读回丢字段） | 同一份字符串存盘前后一致；如果是存储问题，**当次**校验就该失败 |
| 校验判据太严（`/member` 接口变了） | `verify()` 只在 `isNeedLogin(code)` 或 HTTP 401/403 时判过期；模型/其他错误码都返回 `Valid`。而且"当次通过、之后永远不过"是**状态相关**的，不是判据相关 |
| cookie 里少了某个键 | `readCookies()` 多 host 合并后落的是完整快照；且当次校验用的是同一份 |

### 五、修法

`Http.kt` 加两个拦截器（`stashExplicitCookie` / `restoreExplicitCookie`）：

- **application 位**：请求若自带非空 `Cookie`，把它的值收进 `Request.tag`（`ExplicitCookie`）。
- **network 位**：从 tag 取回来，`header("Cookie", …)` 写回 —— 此时晚于 `BridgeInterceptor`，必然生效。

**为什么不用"塞一个自定义头"**：那会把这份凭据**多发给服务端一遍**，有的站直接 400。

**为什么不用"换个没有 jar 的 client"**：jar 是站点解析与播放防盗链**必需**的
（§4.53 那类跨子域签名 cookie），而 `mediaClient` 是 `client.newBuilder()` 派生的同一套配置，
拆 client 等于把这条能力在别的路径上悄悄关掉 —— 又是"改一处漏一处"。所以修在**拦截器层**，
`client` / `fastClient` 显式挂、`mediaClient` 靠派生继承（守卫 `E18d/E18e` 钉住这两点）。

### 六、纪律沉淀

1. **"改了 A 却影响 B"最典型的形态是"第三方库替你改了 B"**：这里没有任何一行我们的代码动过 `Cookie` 头，
   是 OkHttp 的 BridgeInterceptor 干的。凡是"显式传的头"与"库自己管理的状态"**同名**，就要问一句谁后写。
2. **拦截器顺序 = 语义**。application 位与 network 位差一个词，行为完全相反且**零报错**。
   凡是"必须晚于某个内置拦截器"的逻辑，一律配一个**错位对照组**（E1 那种）。
3. **症状里的时间信息是判据**（"登录**当次**是好的"）—— 它把"凭据没用"与"凭据被弄坏"分开了，
   直接排除了一半假设。上报 bug 时把"什么时候是好的"写清楚，价值极高。
4. **实验装置要带"证明观察点有效"的对照组**（C 组摘 jar）—— 否则"第 2 次收到 `srvmark`"也可能
   只是探针写错了。

### 七、未做

- **真机验证**：`adb devices` 仍为空。"修好后登录不再掉"只能在设备上确认（逻辑上有实验支撑）。
- **`DriveStore.state()` 的 `bad_` 标记是粘性的**（只有 `verify()` 成功或重新登录才清）。
  已经处于"过期"的用户装新版后，进账号页会触发一次 `verify()` → 成功即自动恢复；真失效的仍需重登一次。
- **多域名回退**：一个站配多个域名时，App 不会在域名间自动回退（清单 `docs/网盘站源清单.md` 里给了全部域名，
  目前靠用户手换）。
